# Agent instructions

## Development workflow

Each rule says how, then why. Commands and options: [docs/BUILDING.md](docs/BUILDING.md#development-loop); what each check covers: [docs/RELEASE_CHECKS.md](docs/RELEASE_CHECKS.md).

- **Inner loop.** After each edit: `cmake --preset dev && cmake --build --preset dev && ctest --preset dev` (Ninja and ccache on `PATH`; `CC=gcc CXX=g++` for gcc). `ctest --preset dev` runs the `tier-generic` tests, model-free, in about 2 s. For the rest, configure once with `cmake --preset dev -DDUCKTAPE_TEST_MODEL=PATH` and run `ctest --preset dev-real` (every test), or one tier or category: `ctest --test-dir build-dev -L '^tier-specialized$'`, `-L '^cat-faults$'`, `-R '^tokenizer-scaling$'`. Why: the dev preset compiles tests and core at -O1 with precompiled JSON headers through ccache, does not relink tests when only the library's content changed, and hashes relative paths so every worktree hits the same cache, so a one-file edit rebuilds in seconds.
- **Batches.** Design the whole batch first, then run each slow check (the real model, `validate.py --full`, the host gates, CI dispatches, the soak) once per batch, never per change. When checks fail, collect every failure, fix the root causes together, then rerun only what failed (`python3 scripts/verify.py --rerun-failed` or `--only JOB`, `validate.py --phase test --from BUILD --checks CHECK`). Why: each slow run costs minutes to hours, whatever number of edits precede it.
- **Fast path, specialized paths.** A branch push runs only `policy` and `generic-linux-x64`. Windows, macOS, arm64, musl, the browser, each binding, sanitizers, fuzz, the reference probe and the real model are specialized paths: each runs when its inputs change (the categories in `scripts/ci_paths.py`), on demand, or once after a batch through `python3 scripts/verify.py`, which runs the stale local jobs, dispatches `native.yml` (`mode=verify`) for the stale CI jobs, and prints one verdict with each job's time against its budget. Options: `--list` (what is stale; runs nothing), `--local` or `--ci` (one side; `--ci` needs a clean tree pushed to its branch), `--all` (every job, `scope=all`), `--only JOB[,JOB]`, `--real-model [--model PATH]`, `--emsdk DIR` (browser builds), `--rerun-failed`. Full verification (the candidate and qualify runs, `scripts/qualify-host.py`) happens before a release. Why: one slow specialized path must never slow the feedback on every other change.
- **Before merging to main.** Push the branch and run `python3 scripts/verify.py` (every job whose inputs changed since its last trusted pass, local and in both workflows; add `--real-model` when results can change), and merge only when it passes; `--all` reruns every job regardless, for changes the input categories cannot see. Why: a branch push builds only generic Linux; a Linux-only header once broke the macOS build on `main` because no macOS job had run before the merge.
- **Root causes over workarounds.** Find where the failure or the time comes from (`verify.py`'s timing table, `runs[].seconds` in `report.json`, `ctest-junit.xml`, `.ninja_log`, `gh run view RUN --json jobs`) and fix it at the code that owns it. Never loosen a bound, budget, timeout or check to get green; change a number only with a written reason, next to the number and in the commit, why the old one measured the wrong thing. Before 1.0, "it changes the library's bytes" or "it needs requalification" is no reason to hold back an improvement: decide on the measured result. Why: a workaround leaves the cause in place, and the same failure comes back.
- **Tests, not benchmarks.** Register every test with `dtl_add_test(NAME n COMMAND ... TIER generic|specialized|release CATEGORY native|real_model|faults [LABELS timing|qemu] [PROCESSORS n] [SERIAL] [TIMEOUT s] [SKIP_RETURN_CODE n])`. Only fast, model-free tests are `TIER generic`; timing and scaling checks are `specialized` with `LABELS timing` and `SERIAL` (as `tokenizer-scaling`), never part of a correctness test. Check each behaviour once, at the layer that owns it: no checks repeated across native, binding and parity tests, and no tests of what the compiler or another test already catches. Why: the dev loop must stay at a couple of seconds, and a duplicate costs time on every run without catching anything more.
- **CI hygiene.** A new CI job needs an entry in `scripts/ci_paths.py` `JOBS` under its exact `name:` (inputs as categories, profiles, needs), a `JOB_BUDGETS` entry in `scripts/ci_budgets.py` and, if it saves a compiler cache, its own compiler-cache key; `tests/ci-contracts.py` (policy check `ci-contracts`) refuses a job missing from `JOBS`, `needs:` that differ from it, and a cache key saved by more than one job or extending another saved key. One saving job per key, no prefix overlap; restore-only jobs (`binding-*`, `packages-*`) restore their producer's key with `DTL_CACHE_SAVE: 'false'`. Budgets are the p90 of the last 10 runs, each with a comment giving its measured basis. Why: an unclassified job runs on every change or never, a shared prefix lets `scripts/ci-cache-prune.py` (newest two per prefix and ref) evict another job's cache, and a budget without a basis cannot be judged. Release evidence builds follow the compiler-cache rule under Releases.
- **Fast pre-checks.** A new release gate, or a new input to one, comes with a pre-check that finds its likeliest failure in seconds to a couple of minutes, run before any long step: `check-candidate.py --plan` for what the gates can know from the inputs and the plan (evidence keys, axes, the record), the `native.yml` plan step for dispatch inputs, `check-upgrade.py --configure-only` for patches and source coverage at the rehearsal runtime, and the `qualify-host.py` preflight to run them in order, cheapest first. Where none is possible, say why next to the gate. Why: the 0.3.0 qualification found a qualify run that rehearsed the pin against itself after 4.5 hours, a runtime patch that failed to configure after a 3.5 hour library qualification, and a performance budget that failed 35 minutes into a 3.5 hour run, each knowable in under two minutes.
- **Flaky tests.** Treat a flaky test as a race and find it; never add retries, sleeps or longer timeouts. Example: the thread census counted `/proc/self/task` right after `join`, which still lists a joined thread until the kernel releases it; `tests/thread-census.hpp` leaves out exiting threads. Why: a retry hides the race, and it fails again elsewhere, under other load.

## Releases

A release starts only when the maintainer asks for one in the current session. Once asked, carry it out end to end without asking for confirmation at each step, following [docs/RELEASING.md](docs/RELEASING.md): prepare the release commit, qualify the candidate until `scripts/check-candidate.py` (run from a checkout of the candidate commit) reports every gate of every release target passed, assemble and check the assets, tag, create the GitHub release, run `attest-release` and `publish-release`, push `bindings/go/vX.Y.Z`, verify every registry and report. How each check runs is in [docs/RELEASE_CHECKS.md](docs/RELEASE_CHECKS.md).

Stop and report instead of publishing when a gate fails for a reason that is not clearly environmental, when the CI Linux x86-64 library or Node addon differs from this host's even after one uncached redispatch of the candidate run (`-f cache=off`; a match then identifies a compiler-cache fault: record it), when the candidate run is not on the candidate commit or its artifacts have expired, or when anything would need a decision the maintainer has not made ([stop rules](docs/RELEASING.md#stop-rules)). Rerun environmental failures and record why; never loosen a check, budget or timeout. Build this host's gcc release evidence, the reproducibility builds and the browser release builds without a compiler cache. Other builds may use one, the CI candidate builds whose reports are tier-2 evidence included, because every shipped native library and Node addon is compared byte for byte with an uncached build (linux-x64 with this host's gcc build, linux-arm64, windows-x64, macos-arm64 and macos-x64 with their uncached reproducibility builds), so a cache fault fails a gate instead of shipping. The scripts run ccache with `CCACHE_BASEDIR` and `CCACHE_SLOPPINESS` empty, because a `base_dir` makes compiled source paths relative and changes the library's bytes; they refuse binaries with unmapped source paths and record `ccache --show-config`. Sanitizers, the one-hour fuzz and the runtime-upgrade rehearsal run in CI (`mode=qualify`); `scripts/qualify-host.py` runs this host's gates. Never ask the maintainer for secrets or tokens.

## This release host

- **Models.** The primary model is `~/.cache/huggingface/hub/models--ggml-org--Laya-GGUF/snapshots/22265007700297ba9e128297e82540cf28c5d7d4/Laya-Q8_0.gguf`; the additional ones are `laya-multilingual-f16.gguf` and `laya-typed-decisions-q8_0.gguf` in `build-models/` of the main checkout (untracked). If one is missing or fails its manifest hash, rebuild it, never edit a manifest: `python3 scripts/convert-model.py models/laya-multilingual.json build-models/laya-multilingual-f16.gguf --python PYTHON` (and `models/laya-typed-decisions.json build-models/laya-typed-decisions-q8_0.gguf --python PYTHON --quantize LLAMA_QUANTIZE`). `PYTHON` needs `third_party/llama.cpp/requirements/requirements-convert_hf_to_gguf.txt` in a throwaway venv, for example `uv venv --python /usr/bin/python3.12` (the host's default `python3` is 3.15, where the pinned torch did not install); `LLAMA_QUANTIZE` is `llama-quantize` built from `third_party/llama.cpp` with `CC=gcc CXX=g++`. About 2 minutes each.
- **Compilers.** The shell exports `CC=clang`; set `CC=gcc CXX=g++` for gcc builds (the release build is gcc, and its library must match CI's byte for byte).
- **Load.** Heavy parallel load makes the real-model ctest time out and skews its CPU-time ratio tests (`LABELS timing`). Run the host gates through `python3 scripts/qualify-host.py`: it runs the gcc evidence validation and performance alone, then pins the soak to its own physical cores and runs reproducibility, `model_upgrade` (alone beside the soak, since it has the CPU-time tests) and then the browser and package checks on the other cores. Run anything timing-sensitive by hand only on an otherwise idle machine.
- **Scope.** This host builds only Linux x86-64; every other target's packages and evidence come from the CI candidate run, and the sanitizer, fuzz and upgrade evidence from the CI qualify run.
