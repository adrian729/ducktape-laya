# Validation and release checks

How to run each check and produce the evidence each release gate needs. The gates, tiers and acceptance criteria are defined in [QUALIFICATION.md](QUALIFICATION.md) and `release/qualification.json`; `scripts/check-candidate.py` decides whether a candidate passes all of them ([the candidate check](#the-candidate-check)). The release procedure that uses this evidence is [RELEASING.md](RELEASING.md).

Output directories must be new so earlier reports are not overwritten. Keep local outputs under ignored `build*/` paths and attach relevant results to the commit, PR or CI run; do not commit run reports. Models are supplied explicitly and checked against their pinned manifest before real inference; no runner downloads one.

## Native validation

```sh
npm ci --ignore-scripts --prefix tests/typescript
python3 scripts/validate.py --policy all --packages --output build-check-model-free
CC=gcc CXX=g++ python3 scripts/validate.py --full --model /path/to/Laya-Q8_0.gguf \
  --extra-model /path/to/laya-multilingual-f16.gguf \
  --extra-model /path/to/laya-typed-decisions-q8_0.gguf \
  --upstream-reference --test-jobs 1 --output build-check-native
python3 scripts/check-reproducibility.py --output build-repro
```

`scripts/validate.py` configures and builds the library, the Node addon and the native tests with Ninja and the release options, runs the selected checks, and writes `report.json` with every command, log, exit code and the source, runtime, model, fixture and binary identities. Without options it runs the generic checks of a branch push (the `tier-generic` tests, `tests/examples-smoke.py`, the ABI export check and `scripts/check-binary.py`; with `--model` also the `cat-real_model` tests); options add checks ([building](BUILDING.md#validation-runs)). `--full` runs every check of `FULL_CHECKS` and every policy check: every registered native test (`ctest --no-tests=error`, the JUnit test names compared with the required registrations), the Rust, Node, Python, Java, .NET and Go suites (concurrently), the cross-binding comparison of C, C++, Rust, Node, Python, Java, .NET and Go fixture outputs (`tests/parity.py --profile full`), the original and upstream references, the packages, and the policy checks: compiled C/C++/Rust ABI layouts, TypeScript consumers in CommonJS, ESM and bundler modes, artifact identities, browser lifecycle and backend regressions, the Markdown links and the release tooling's own tests. TypeScript test tools are development-only and installed explicitly with the locked command above; `tests/typescript/check.py --node-package NPM_TARBALL --browser-package BROWSER_TARBALL` additionally checks extracted package declarations. Reused candidate source and revision overrides are cleared, and built runtime diagnostics must match the approved compatibility record before any test gate is accepted. `--packages` builds the actual artifacts and runs `tests/package-smoke.py`, which needs no model: outside the checkout, a C program links the native tarball, the npm package loads its addon, the wheel imports its bundled library, and the Maven jar and the NuGet package load theirs, and each must report the recorded ABI version. It also reads the three jars' manifests (the main jar's version and module name, as `java.util.jar` sees them) and checks that the NuGet package loads its bundled library and never a copy in the current directory or on the search path. The ecosystem probes run concurrently, each in its own directory. Installed packages with real inference are checked on the assembled release packages ([installed packages](#installed-packages)), not by `validate.py`. `--reproducibility` adds two independent builds.

**Evidence profiles.** Every report records `selection.profile`, written by the run that produced it and never recomputed. `scripts/check-candidate.py` accepts each profile only where it belongs and requires its checks:

| Profile | Producer | Required |
|---|---|---|
| `host-full` | `validate.py --full` on the release host: the tier-1 `native` evidence and the gcc entry of `native_matrix` | Every `FULL_CHECKS` check and every policy check passed, or skipped with a reason from the platform allow-list; no compiler launcher; `host.github_actions` false |
| `ci-full` | `scripts/merge-validation.py --profile ci-full` in a candidate run's `evidence-<platform>` job (`linux-x64`, `linux-arm64`, `windows-x64`) | The shard checks `ctest`, `references`, `parity:full-a`, `parity:full-b`, `bindings`, `packages` and `policy-platform` passed; the other policy checks ran in the same run's `tooling` job, whose success the run's conclusion carries |
| `ci-compiler` | the same merge with `--profile ci-compiler` for `linux-x64-clang`: the CI clang entry of `native_matrix` | The shard checks `ctest`, `references`, `parity:full-a`, `parity:full-b` and `bindings`; no packages, no policy |
| `generic`, `selected` | every other `validate.py` run (default, or `--checks`, `--bindings`, `--policy`, `--packages`) | Never evidence |

The checker also requires `DUCKTAPE_DEV_BUILD` and `DUCKTAPE_DEV_PCH` recorded `OFF`, phase `all` for `host-full` and `merged` for the CI profiles, and the required registered tests. `--full` refuses (exit 1, `selected_checks: failed`, the checks in `full_refusal.missing`) when any of its checks neither passed nor is a listed platform skip, and refuses before configuring without `--model` or an additional model of the release record, so a forgotten model costs seconds, not a build. Build jobs default to `DUCKTAPE_JOBS`, else `min(CPUs, MemAvailable / 0.6 GB)`; `--test-jobs` (the `ctest -j` level) defaults to 1 with `--model` off CI, because the real-model CPU-time tests need a quiet machine. `--phase build` builds and keeps the build-phase report; `--phase test --from BUILD --checks LIST` runs checks on that build without building, after requiring the library, addon and `CMakeCache.txt` to be the build phase's: CI's shards run this way, and on the host it reruns one failed check without rebuilding.

`--upstream-reference` builds a separate test executable using upstream primitive processing and compares every fixture request, including batch members, without an HTTP server. It never links that processor into the product library. Structured requests are compared through their schema-derived primitive questions (`tests/reference_requests.py`); value projection remains covered by the shared-core contracts. Both sides receive structured values already serialized the way the original Laya writes them, so they render identical prompts. Without this option, the upstream-reference gate stays not run. The probe's own targets may compile through a cache (`--reference-probe-launcher`, default ccache or sccache when on `PATH`): its objects never reach a shipped binary, and a configure-time guard fails if the probe's launcher would reach any target in the library's or addon's link closure (`generated/launcher-guard.json`, recorded in the report).

With a model, `tests/original-reference.py` also runs the original Laya implementation's recorded cases (`tests/original-reference/<model>/`, Apache-2.0, with provenance) through the C consumer at the prompt length the original Laya runs the checkpoint at: the `original_reference` gate. Input token counts must match exactly, and probabilities must stay within 0.05 with unchanged decisions. On near ties (the original's top two within 0.05) the decision may differ, since the model is undecided and quantization noise can reorder options; the probabilities are still gated. The original truncates over-long input by default, so its long-state and many-option cases run with `overflow: truncate_end`, and their `state_tokens` and `state_tokens_dropped` must match too. Cases for features the core does not support (the embedding shortlist) must still be refused; when one starts passing, it moves into the supported set.

`--extra-model PATH` (repeatable) qualifies an additional pinned model, one listed under `additional_models` in `release/compatibility.json` (the multilingual and typed-decisions models), matched to its pinned manifest by file hash. Each runs the `original_reference` gate against its own recorded cases and, with `--upstream-reference`, the upstream comparison. The results go to `additional_model_gates` in `report.json`. `check-candidate.py` requires both gates passed for every additional model, so a candidate cannot qualify without them. The primary model is still passed with `--model`.

The core bounds the temperatures stored in a model to [0.5, 5], as the original does; llama.cpp applies them unbounded. The upstream-reference checks therefore compare our probabilities re-expressed at the stored temperature (exact up to rounding, since probabilities are a softmax of scores over the temperature). Sanitizer, stress, browser and platform evidence remain separate; the runner does not silently transplant historical results to a different binary. This runner covers a subset of release gates and cannot approve a release by itself. A successful normal exit means its selected checks passed.

`tests/examples-smoke.py` (run by the validator on non-Windows hosts, model-free) checks that every `examples/*.json` and `examples/presets/*.json` request passes the library's request validation (through a router engine, which validates before it loads a model) and that `examples/decide.c` and `decide.cpp` compile and fail cleanly without a model.

The binding suites also test how each package finds its library. On Windows the Java suite (`windowsExtraction`) extracts and loads the bundled DLL, reuses an existing copy, honours `-Dducktape.laya.tmpdir` and falls back to a fresh owner-only directory; with `icacls` it adds an inheritable Everyone entry to the base directory before and after extraction (it must reach neither the shared directory nor the copy, while it propagates to an ordinary sibling directory), lets Everyone write the shared directory and copy (the loader must make them owner-only again), and, when the suite runs elevated (GitHub's runners are), makes SYSTEM own the copy (it must be rewritten) and the directory (it must be refused); unelevated it prints a SKIP line for those. Elsewhere the owner and ACL cases are skipped. On every platform it checks that stray entries in the shared directory are removed, that the directory name depends on the owner, and (Linux and macOS) that the private extraction directory is gone while the library stays mapped. The Node and Java suites test musl detection with simulated loader directories (`ld-musl-*` without `ld-linux-*`), and CI's `musl` job runs the assembled npm package and jar in Alpine containers (`tests/musl-packages.sh`): both must fail with status 7 and the glibc/musl message, and npm must refuse the Linux-only npm package. On Linux and Windows `tests/package-smoke.py` runs the NuGet consumer from a directory holding a copy of the library and with another copy on the search path (`PATH` on Windows, `LD_LIBRARY_PATH` on Linux): the process must map only the bundled `runtimes/<rid>/native/` library; with the bundled copy removed it must fail with a status-7 "was not found" `LayaException` on Windows (neither copy is searched) and load the `LD_LIBRARY_PATH` copy on Linux (never the current directory's). On Linux it also checks that the npm package's addon has a `DT_RPATH` (`$ORIGIN`, no `DT_RUNPATH`) and maps only its own library with another copy on `LD_LIBRARY_PATH`.

**Compiler caches.** `--compiler-launcher {none,ccache,sccache}` (default `none`) compiles the product targets through that cache, passed as `CMAKE_C_COMPILER_LAUNCHER` and `CMAKE_CXX_COMPILER_LAUNCHER`; `GGML_CCACHE` is always `OFF`, because ggml otherwise uses any `ccache` on `PATH` without saying so. ccache runs with `CCACHE_BASEDIR` and `CCACHE_SLOPPINESS` empty and `CCACHE_COMPILERCHECK=content`, overriding the user's configuration: a `base_dir` hands the compiler relative source paths that `-ffile-prefix-map` does not map, which changes the library's bytes. The report records `compiler_launcher`, the launcher variables under `build_options` and `ccache --show-config` under `ccache_config`; the runner refuses a build whose `base_dir` is not empty, and after the build (as does `package-native.py`) a library or addon holding a compiled-in source path outside the mapped directories, that is one that does not begin, after an optional `./` (GCC keeps it, Clang drops it), with a top-level entry of the checkout or `build` (`release_support.require_mapped_source_paths`). `--cmake-arg` cannot set the launcher variables, `GGML_CCACHE` or the dev options (the runner passes its own values last and, after configuring, checks what the CMake cache holds). Which builds may use a cache:

| Build | Cache | Why |
|---|---|---|
| Push, verify, weekly and warm-cache CI builds | ccache (Linux, macOS), sccache (Windows) | Feedback only |
| CI candidate builds (every platform) | On; off with the dispatch input `cache=off` | Every shipped library and addon is compared byte for byte with an uncached build: linux-x64 with this host's gcc build (`artifact_integrity`), linux-arm64 and windows-x64 with their uncached reproducibility builds. `cache=off` is the escape when the bytes differ: one uncached redispatch tells a cache fault from a real difference |
| This host's gcc evidence build (`validate.py --full`) | Off (`host-full` requires it) | It is the uncached build CI's linux-x64 bytes are compared with |
| Reproducibility builds (host and CI) | Off | Their purpose is independent fresh compiles |
| Reference-probe-only targets | On | Never in a shipped binary; guarded as above |
| Sanitizer, fuzz and upgrade builds (`check-sanitizers.py`, `check-fuzz.py`, `check-upgrade.py`) | Optional (`--compiler-launcher ccache`; the CI qualify jobs use it) | Instrumented or rehearsal builds, never shipped |
| Browser release builds (`build-browser.py`) | Off by default; `--compiler-launcher ccache` for rehearsal builds | No gate compares the shipped `.wasm` with an uncached build; `package-browser.py` refuses a build that recorded a launcher |

`check-stress.py` builds `laya-stress` in the validated build directory and keeps its configuration.

With `--model` on Linux x86-64, the runner requires the `cpu-guard` test to be registered (it is, on every Linux x86-64 build with `python3`); the test itself needs `qemu-x86_64` and `node` on `PATH` when it runs. Each report also records the Rust, Go, Java, .NET and Python versions it found under `toolchains`, and `host` (whether it ran on GitHub Actions, the hostname, system and machine).

## Continuous integration

Two workflows. `native.yml` ("Native checks") holds the release targets (Linux x86-64 with gcc and with clang, Linux arm64, Windows x64), the packaging chain, sanitizers, fuzz and every dispatch mode; the Windows jobs are a separate subgraph of it that never gates Linux, except in the packaging chain. `platforms.yml` ("Other platforms") holds macOS arm64, with the same change logic; it is never part of a candidate run, so a macOS failure cannot fail release evidence. Workflow dependencies are pinned by commit and toolchain versions are explicit. Workflow definitions alone are not release evidence; CI does not publish packages or update dependencies.

**What runs.** A first job, `changes` (`scripts/ci-changes.py` with the tables of `scripts/ci_paths.py`), decides which jobs run; every other job runs only when its name is in that list. A job is a verification unit by its exact `name:`.

| Event | Runs |
|---|---|
| Push to a branch other than `main` | `changes`, `policy` with the policy checks whose inputs changed, and `generic-linux-x64` when stale. Nothing else |
| Push to `main`, or any merge commit | Every job of the push profile (below), unless the tree equals the tree of a commit at which every push-profile job is verified (identical-tree skip: nothing runs), or differs from such a commit (one of its parents or their first five first-parent ancestors) only by documentation that no job but the policy checks reads (`ci_paths.is_inert`: `docs`, `AGENTS.md`, `README.md`, ...): then only `policy` runs, with the checks those files select. Any other path, an unclassified one, a workflow or classifier change, or an API failure keeps the whole profile |
| `pull_request` | As a branch push; its runs are never records |
| Dispatch `mode=verify` (default; what `scripts/verify.py --ci` sends) | `scope=affected`: the stale push-profile jobs, and with `real_model=true` the stale real-model jobs; `scope=all`: all of them; or `scope=JOB,JOB`: those |
| Dispatch `mode=candidate` | The candidate profile: everything, every platform, never skipped ([candidate run](#release-targets-and-the-ci-candidate-run)) |
| Dispatch `mode=qualify` (inputs `runtime`, `fuzz_seconds`, default 3600) | The long instrumented gates ([qualify run](#long-and-instrumented-gates)) |
| Dispatch `mode=warm-cache`; nightly schedule (03:17 UTC) | Build-only jobs per cache configuration (`warm-linux-x64`, `warm-linux-x64-clang`, `warm-linux-arm64`, `warm-windows-x64`, `warm-asan`, `warm-tsan`, `warm-fuzz`), always, so `main`'s caches never age out; then `cache-prune` |
| Weekly schedule (Saturday 04:41 UTC; `platforms.yml` too) | `scope=all` with the real model: the drift check of runner images and toolchains |
| Dispatch `mode=experiment` | `bench-windows-x64` ([Windows benchmark](#windows-benchmark)) |

The dispatch input `cache=off` builds every job of the run without a compiler cache. A newer push to a branch other than `main` cancels that branch's older push run; runs on `main`, pull requests, dispatches and schedules are never cancelled.

**Push profile.** `policy` (`scripts/check-policy.py --stale`), `generic-linux-x64` (gcc), `generic-linux-x64-clang` (pinned clang, plus `tests/reconfigure.py --edit-copy`: reconfiguring the finished build recompiles nothing, and an edited patched runtime copy is restored and recompiled alone), `generic-linux-arm64` and `generic-windows-x64` each run `validate.py`'s generic checks (`check-binary.py` checks the glibc floor and ELF hardening, arm64 PAC, Windows exports and `/guard:cf`); `generic-windows-x64` also runs `abi-layouts` and `packaging-identities` when their inputs changed. `binding-<language>-linux-x64` and `binding-<language>-windows-x64` run one binding's model-free suite with only that toolchain installed. `packages-<platform>` build each platform's fragment, `assemble` merges them, `assembled-<platform>` install the result on every platform and `musl` runs the assembled npm package and jar in Alpine containers (`tests/musl-packages.sh`). `sanitizers` builds the `sanitize` preset and runs the `tier-generic` tests under ASan and UBSan (no recovery, no suppressions); `fuzzer` builds `laya-input-fuzzer` with the `fuzz` preset and runs a 60-second libFuzzer smoke from the generated corpus (it exercises the harness; the one-hour campaign is the qualify run's). `reproducibility-windows-x64` runs `check-reproducibility.py`, uncached. In `platforms.yml`: `generic-macos-arm64` and `binding-<language>-macos-arm64`.

**Real-model profile** (dispatch with `real_model=true`). `build-<P>` for `linux-x64`, `linux-x64-clang`, `linux-arm64` and `windows-x64` runs `validate.py --phase build` with the model and the reference probe and uploads the build directory as a tarball (without object files and static archives; restored at the same absolute path, kept 7 days); the shard jobs restore it and run `validate.py --phase test --checks ...`: `native-<P>` (or `ctest-windows-x64` and `references-windows-x64`) the native tests and references, `parity-<P>` the `smoke` parity profile, `bindings-real-<P>` the real-model binding suites when a binding changed. The clang leg runs only its native checks. The shard tables are data (`SHARDS` in `scripts/ci_paths.py`), so rebalancing needs no workflow edit.

**Staleness.** A job J is verified at commit X when a run of the same workflow in this repository with head commit X and event `push`, `schedule` or `workflow_dispatch` has a job named exactly J that succeeded (`pull_request` runs never count: their tree is a synthetic merge; a partial dispatch counts only for the jobs it ran). J is stale when no commit among HEAD, its parents and its first-parent ancestors (at most 50) verifies it, or when the diff since the newest one touches J's input categories, the `ci` category (the workflows and the classifier: every job is stale) or a path in no category. Any API or git failure makes every job stale (fail open: run everything). The run set is then closed: a job that reads another job's artifacts of the same run pulls that job in (a shard its build, `assemble` the three fragments), and a rerun fragment pulls in the packaging chain after it. `tests/ci-changes.py` tests these rules offline; `tests/ci-contracts.py` checks that every workflow job's name and `needs:` edges match `JOBS` and that every saved cache key belongs to one job.

**Toolchains.** Every Linux x86-64 clang job (generic, build, shards, sanitizers, fuzz, qualify) uses LLVM 22.1.8 from `.github/actions/setup-llvm`: the official release archive, checked against its sha256 before a fixed member list is extracted, and cached; the job fails unless `clang --version` reports 22.1.8. The ThreadSanitizer Rust leg uses `nightly-2026-10-17` with `rust-src` (`RUST_NIGHTLY` in `scripts/check-sanitizers.py`, recorded as `rust_toolchain`). Windows uses the runner image's clang-cl; its reports record the image (`build_environment`). Ninja comes from `.github/actions/setup-ninja`.

**Caches.** Compiler caches are keyed `ccache-<os>-<arch>-<compiler>-<configuration>-<pin hash>` (sccache on Windows), one key per job that saves, none a prefix of another, restored by prefix. Only build and warm-cache jobs save; shards, binding and stress jobs restore only. The model cache (keyed by the model's sha256, checked with `verify-model.py` after restore), the evidence-build seeds and the extracted LLVM are saved on `main` by the nightly, so every branch can restore them; on a miss the build job saves the model. Cargo, NuGet and Go caches are kept too (Go's build cache keyed on the Go version, the `go.mod` files and `include/ducktape_laya.h`, since Go's test cache does not see the library's contents; its tests run with `-count=1`). `scripts/ci-cache-prune.py` (the nightly `cache-prune` job) keeps the newest two entries per key prefix and ref and deletes the entries of branches that are gone or merged into `main`. Each build job writes `ccache -s` (or `sccache -s`) to the step summary. The build jobs use 4 parallel jobs (4 vCPUs; macOS 3). Windows jobs first add Defender exclusions for the workspace, the temporary directory and the toolchain caches.

**Budgets.** `scripts/ci_paths.py` holds wall-time budgets: per workflow (`BUDGETS`: branch push 100 s, docs-only 45 s, `verify.py --ci` model-free 300 s, real-model dispatch 480 s, candidate 660 s) and per job (`JOB_BUDGETS`), each the p90 of the last 10 runs with its measured basis in a comment. `scripts/verify.py` prints each job's time against its budget. A budget changes only with a written reason why the old number measured the wrong thing.

## Performance budgets

The benchmark (`tests/benchmark.py`, one fresh process per run) records model open/close, first and warm p50/p95/p99 latency for small, structured, near-limit and batch requests, two engines in concurrent threads, router cold loads with evictions, cancellation response and deadline overshoot, RSS, descriptors and threads. Repeated outputs must match and descriptors/threads must return to their starting counts. Budgets are frozen per profile, model, thread count and reference CPU from at least three independent runs, then candidates are checked against them:

```sh
python3 tests/benchmark.py /path/to/Laya-Q8_0.gguf --report build/bench-1.json  # repeat per run
python3 scripts/performance-budgets.py derive build/bench-{1,2,3}.json --output release/budgets/native-performance.json
python3 scripts/performance-budgets.py check build/bench-candidate.json
```

Limits are the worst baseline value times a declared headroom (1.5 for time, 1.25 for memory); leaks have none. The committed budgets in `release/budgets/native-performance.json` were frozen from a 0.1.0-era baseline (source commit `baaf568`, an ancestor of `v0.1.0`); a 0.2.0 build still met them on 2026-10-21. Each additional model has its own budget, named by `performance_budgets` in its manifest (`release/budgets/native-performance-<model id>.json`, derived 2026-10-21 from three 0.2.0 runs); `tests/benchmark.py` takes any pinned model, and check-candidate reads the benchmark report for each additional model from the evidence key `performance_<model id>`. They detect regressions on the reference host, not portable latency promises. `scripts/qualify-host.py` runs them on the otherwise idle release host (step 2); by hand, run without competing builds or inference. A report carries its environment: `host_state` holds the load average, every thermal zone (`x86_pkg_temp` is the CPU package), each CPU's `scaling_cur_freq` and the kernel's thermal-throttle counters before the run, after each workload, after the cancellation checks and after the run, and `settle` what the optional wait did (`--settle-temp-c`, `--settle-load`, `--settle-timeout`; `qualify-host.py` passes 75 C, load 1 and 900 s, then measures anyway and records `settled: false`). `performance-budgets.py check` prints a `host` summary (hottest package, lowest mean frequency, highest load, throttle events), so a failed budget can be attributed to a hot, throttled host or to the code; the budgets and the check are unchanged. A failure with `settled: false` or throttle events is rerun with `qualify-host.py --replace` only after the host cooled; the failed report stays under `superseded/`.

### Performance budget re-measure

`qualify-host.py` gives a performance budget check that fails one automatic re-measure, and only that check. After the failure it runs the same benchmark again, which first repeats the settle wait (package at most 75 C, load at most 1), and checks the new report against the same, unchanged budget file. The second attempt must pass; if it fails the step fails, and so does the run (the run stops there: the soak and everything after it would be rerun once the library or the host changes). Both attempts stay in the evidence: the first report is `performance/ID.json`, the second `performance/ID.remeasure.json`; the `performance` (or `performance_ID`) evidence key names the second, whose `remeasure` object records the attempt number, the first report's relative name and sha256 and the first check's output, and `qualify-status.json` marks the step `remeasured`. Why: the budgets are p90s of runs on a laptop-class host, whose failures cluster in thermal noise (the 0.3.0 run failed `cancellation_response_seconds` 0.04386 against 0.04256 at 89 C with 246,604 throttle events and load 5.2, after a 35 minute wait for a 3.5 hour run). One recorded re-measure after the host settled again is standard benchmark practice and does not loosen anything: no budget, tolerance, headroom or timeout changes, a real regression fails twice, and a benchmark that crashed or leaked (its own exit status) is never re-measured. A third attempt is never made; rerun `qualify-host.py --replace` by hand after the host cooled, as before.

### Fast pre-checks of the release qualification

Each gate of the release has a pre-check that finds its likeliest failure before the long run starts, in seconds to a couple of minutes: `check-candidate.py --plan` (the gates against the candidate's record, documents, reuse table, rehearsal runtime and model axes, and the evidence keys the plan will produce), the `native.yml` plan step (a qualify run needs a runtime other than the pin), and `check-upgrade.py --configure-only` (runtime patches and source coverage at the rehearsal runtime, no build). `qualify-host.py` runs the first and last in its preflight. A new gate comes with its own where one is possible ([AGENTS.md](../AGENTS.md#development-workflow)).


### Windows benchmark

There are no Windows budgets, and Windows inference is 1.2 to 1.5 times slower than Linux x86-64 on comparable runners. The `bench-windows-x64` job (`native.yml` dispatched with `mode=experiment`) measures it: it builds the library with the product flags and with `/clang:-O2`, checks from the compile commands that the two builds really differ (clang-cl turns the product's `/O2` into `-O3` for the compiler, so `/clang:-O3` would build the same bytes) and fails if their DLLs are identical, records the page faults and time of opening the model, and runs `tests/benchmark.py` on each. It is data, not a gate: a flag change would be adopted only if faster with byte-identical outputs. The first run gave the same p50 latency for both variants, so the optimization level does not explain the gap ([roadmap](ROADMAP.md#build-ci-and-packaging)).

## Stress and soak

The native stress program `laya-stress` (`tests/stress.cpp`, built on demand: `cmake --build BUILD --target laya-stress`) runs rounds of real use against one model:

```sh
build/laya-stress /path/to/Laya-Q8_0.gguf 40                               # 40 rounds (10 to 10,000)
build/laya-stress /path/to/Laya-Q8_0.gguf --seconds 3600 --min-rounds 40   # at least an hour and 40 rounds
build/laya-stress --check-series RESULT.json                               # the late-growth rules on a recorded result
```

Every round exercises open/use/close, malformed input, deadline recovery, a cancellation inside the forward pass (at a should_cancel poll counted to fall in the middle of the graph, so ggml abandons it) and the reuse of that context, and concurrent callers on one handle with two inference threads; periodic rounds add mixed batches, an independent second engine, and a router whose two hard-linked model paths (created in the working directory, which must share the model's filesystem) force cold loads and evictions. A duration run completes at least its rounds floor (default 10), then runs the concurrent-caller check once more. Progress goes to stderr; the result line on stdout holds the elapsed time, the resource measurements, `closed_rss_kib_by_round` (the closed RSS after every round, in KiB) and `late_growth` (both rules' statistics). It is written on success and on every failure after the first completed round (`status: failed` and the `failure`), so a failed soak keeps its series.

**Per-close limits.** After every close, descriptors and threads must return to their baseline and the closed RSS must stay within 128 MiB of it, the declared allocator retention allowance. On Windows the program measures committed private bytes (`PrivateUsage`) instead of `VmRSS`, the handle count instead of descriptors, and threads from a Toolhelp snapshot ([details](#release-targets-and-the-ci-candidate-run)).

**The memory reading.** Each closed-RSS reading first returns the allocator's free memory to the operating system, so it measures live memory, not what the allocator happens to keep, while every round still runs with the allocator as it is. Under AddressSanitizer the program calls `__sanitizer_purge_allocator()`: freed chunks wait in ASan's quarantine (256 MiB by default) to catch use after free and stay resident, so without the purge the closed RSS grew with the quarantine, not with the program (about 97 MiB of a 10-round run's growth); LeakSanitizer is unaffected, since it reports at exit. With glibc it calls `malloc_trim(0)`: free memory stays in the arenas the round's threads happened to use, and the closed RSS moved between plateaus about 2.4 MiB apart (a 3 MiB step in a pinned 631-round run), more than the soak rule's 2 MiB median limit. Other allocators (Windows, macOS, musl) are read as they are.

**Late growth.** Two rules apply to the closed-RSS series of N rounds (`tests/stress_rule.hpp`, tested model-free by `stress-rule`):

- From 40 rounds (every run): the last quarter's median must not exceed the second quarter's by more than 32 MiB; the first quarter is warm-up.
- From 1,000 rounds (the soak rule): the first quarter is skipped (it holds Windows' warm-up and any early allocator step); the last quarter's median must be at most 2 MiB above the second quarter's, and the least-squares slope over rounds [N/4, N) at most 1 KiB per round.

A single allocator step of height h in the middle of the window adds about 2h/N to the slope (0.3 KiB/round for a 148 KiB step at N = 1,000), so a step passes and sustained growth of about 1 KiB per round fails, the leak a long run exists to find. Under the 32 MiB rule alone, the former eight-hour soak let growth of 5 to 7 KiB per round pass.

**Budgets** (`release/qualification.json`): the candidate soak runs `candidate_soak_seconds` (10,800 s, three hours) and at least `candidate_soak_rounds` (1,000) rounds, so the soak rule always applies; it also serves the routine stress gate (`routine_stress_seconds`, one hour). The tier-2 short stress runs `short_stress_seconds` (300 s) and at least `short_stress_rounds` (40), under the 32 MiB rule only (100 to 135 rounds at 2.2 to 3.0 s per round on the CI runners). A run continues past its seconds until it reaches its rounds floor, and its budget is met only when both are. A short smoke run does not satisfy any gate, and this native test does not cover browser memory.

`scripts/check-stress.py` runs `laya-stress` with identities recorded:

```sh
python3 scripts/check-stress.py /path/to/Laya-Q8_0.gguf --build build-validation --seconds 10800 --output build-soak   # the candidate soak
python3 scripts/check-stress.py /path/to/Laya-Q8_0.gguf --build BUILD --prebuilt --budget short --output build-stress  # the tier-2 short run
```

It records the library, test program and model identities before the run and checks them unchanged after, passes the rounds floor as `--min-rounds` (default: the budget's floor) and records `required_rounds` and `qualification_budget_met`. It kills the run after max(seconds, rounds floor × 20 s) + 1,800 s, or as soon as `laya-stress` has written no progress for 900 s (a hang). The 20 s per round is the margin over the slowest measured rate: on the release host's pinned soak cores, beside the other gates, a round takes 11 to 14 s, so there the 1,000-round floor binds and the soak runs about 3.5 to 4 hours. `--prebuilt` uses the build directory's `laya-stress` without building (a restored CI build). A failed run that completed a round still records its result line.

**Why this soak.** The soak runs on the candidate's exact library bytes, on the qualified tier-1 machine, pinned by `scripts/qualify-host.py` to all threads of its highest-numbered physical cores (`--soak-cores`, default 2) while the other gates run on the remaining cores, never on a soak core's SMT sibling, so the gates beside it share no core with it. Its length is set by what it must detect: three hours and 1,000 rounds give the soak rule a long enough series to separate sustained growth of about 1 KiB per round from allocator steps and noise, and the one run serves both the soak and the routine stress gate.

## Fault injection and the CPU guard

`real-faults` (`tests/faults.cpp`, Linux, registered with a test model) feeds damaged models to `dtl_open`: empty, non-GGUF and unreadable files, a directory, truncation from the header to the last byte, and in-place corruption of the magic, version, tensor/metadata counts, a string length, the decision type, temperatures and the head budget. Each must return `DTL_MODEL_ERROR` with a message and no descriptor leak; corrupted tensor bytes are not detectable without the host's SHA-256 check. It then injects allocation failure: model loading under an address-space limit, and failing the Nth C++ allocation of `dtl_execute` (the first 128 points, then every 97th) and of `dtl_open` (every point through 32, then every 1.5x). Request failures must return `DTL_OUT_OF_MEMORY`; failures absorbed internally must still produce exact results; the engine must keep returning exact results afterwards. `real-c-faults` (same executable, `--c-allocations`; not in sanitizer builds) fails C allocations (`malloc`, `calloc`, `realloc`, `posix_memalign`, `aligned_alloc`, `memalign`), each in its own child process: every one of a `dtl_execute`, and of a `dtl_open` the first 64, then every 6th (ggml aborts by design at most of the later open points; the sampled points keep every failure class). Every point must end in an exact result, `DTL_OUT_OF_MEMORY`/`DTL_MODEL_ERROR`, or `SIGABRT` from ggml's own allocation checks; any other signal fails (an unchecked NULL). At least one inference point must reach the caller as `DTL_OUT_OF_MEMORY` and leave the engine returning exact results. A last sweep alternates two states with different text and tokens and fails each C++ allocation of a call that replaces the cached state tokens, on one engine; the last points, where the cache is replaced, run again on a new engine each, 8 spread over the last 64. The cached tokens must always belong to the cached text (a request for the cached state with a token limit its own tokens exceed must still be rejected) and results must stay exact.

`real-runtime-faults` (same executable, `--runtime-faults`) fails work inside a forward pass, each in its own child process: worker-thread creation under `RLIMIT_NPROC` and, outside sanitizer builds, the CPU work buffer's growth for a request larger than the baseline. Each call must return `DTL_OUT_OF_MEMORY` and the engine must then return exact results for smaller and larger requests; after the failed growth, the next smaller request must allocate a new work buffer instead of reusing the released one. Where `RLIMIT_NPROC` is not enforced (root), that check cannot run: the test exits 77, which CTest reports as skipped (never as passed) and `validate.py` records under `skipped`. `real-api-faults` (`tests/c-api-faults.cpp`, Linux, registered with a test model, not in sanitizer builds) calls the llama.cpp and ggml C functions the library uses directly (model loading, context creation, tokenization, `llama_encode`, buffer creation) and fails each C++ allocation on the calling thread in turn (every point up to 16, then every 1.5x): each call must return its own failure value (NULL, a negative status or `llama_tokenize`'s sentinels) and nothing may be thrown out of it; the functions called without a failure value must not allocate at all. Through link-time wrappers it also fails allocations the sweep does not reach: the first construction of the CPU backend's extra buffer types, which must fail the model load and be built by the next one, and each call site's dummy buffer record, which model loading creates hundreds of times to ask whether a buffer type supports a weight (the load must then return NULL; taking the type as supported crashed it). GGUF reading must free everything it allocated when it returns NULL. It guards the Windows build (clang-cl `/EHsc`), where an exception leaving an `extern "C"` function is undefined behaviour, and cannot see an exception that llama.cpp lets out of an inner C function and catches itself (`c-api-no-throw.patch` lists those). `ggml-faults` (`tests/ggml-faults.cpp`, Linux, model-free) checks the same two failures directly on ggml, plus a refused first, second or third worker thread (the started ones must be joined). `tokenizer-partition` (`tests/tokenizer.cpp`, model-free, generic tier, on eight of upstream's vocabulary-only test files) compares token sequences with `tests/fixtures/tokenizer-partition.txt`, recorded with the unpatched runtime. `tokenizer-scaling` (specialized tier, `timing`, run alone) checks on the gpt-neox and llama-spm vocabularies that tokenization time grows linearly with the number of special-token matches (4 KiB against 128 KiB of matches, in the thread's CPU time: linear growth is x32, the limit x96, the quadratic partition about x1000); `real-tokenizer` does both for the test model's vocabulary. Sanitizer builds do not time (the instrumentation slows tokenization several times over): they print `NOT APPLICABLE`. `real-control-tokenize` (`tests/control-tokenize.cpp`, every platform, registered with a test model; further models may be passed after it) checks in the calling thread's CPU time that a deadline or cancellation at a tenth of a 1 MiB state's tokenization ends the call within half of it for text that special tokens split into short pieces (double-spaced English and long words; newline-separated lines for the additional models), and that a cancellation callback calling another engine during tokenization leaves the call cancellable. `real-decision-head` compares the selected decision head's scores with the full graph's. With `--extra-model`, `validate.py` also runs the tokenizer golden entries and the decision-head comparison on each additional model and `real-control-tokenize` with each additional model, and records them under `additional_model_gates` (`tokenizer`, `decision_head`, `control_tokenize`); `check-candidate.py` requires all three for every additional model.

`real-control` (`tests/control.cpp`) checks cancellation and deadlines. It counts the `should_cancel` polls of a call (the library's own checks, tokenization, and ggml's abort callback after every graph node), takes the forward pass's share from the difference between a one-window and a multi-window `scan` request with the same tokens, and stops calls at chosen polls inside the graph: a cross-thread cancel held at the middle poll, a one-shot cancel that must stay latched (and end the pass early: the calling thread's CPU time from the stop to the return, summed over calls, must be under half that of the rest of full passes), and a deadline expiring at the middle poll. Each must end with its own status at exactly that poll and leave the context giving unchanged results. Separately, deadlines and cancellations at a tenth of a 1 MiB state's tokenization time must stop tokenization within half of it (fastest of three calls each), in the calling thread's CPU time as in `real-control-tokenize`, which load does not stretch. On Linux it also checks the automatic thread count: with the affinity mask cut to one CPU, an engine opened with `threads` 0 starts no worker threads during a pass (counted in `/proc/self/task`, against one worker for `threads` 2). Where the host forbids changing the affinity (a sandbox), that check cannot run: the test prints a `SKIPPED:` line and exits 77 after its other checks, which CTest reports as skipped, never as passed.

`cpu-guard` (`tests/cpu-guard.py`, x86-64, registered with a test model when `qemu-x86_64` and `python3` are found; not in sanitizer builds) runs a C probe and the Node binding under QEMU user-mode CPU models. Nehalem (no AVX) and Sandy Bridge (AVX, no AVX2/FMA/F16C/BMI2) must return `DTL_UNSUPPORTED_PLATFORM` naming the first missing feature, with `dtl_info` listing every missing one. QEMU executes AVX-family instructions regardless of the emulated CPU, so the probe runs with execution logging and each executed block is decoded: no instruction from a feature the emulated CPU lacks may run. An emulated CPU with every feature must open the model, and the scan must see AVX/AVX2 there (positive control). It does not replace a run on physical older hardware.

## ThreadSanitizer and fuzzing

ThreadSanitizer covers the native library, llama.cpp/ggml (its own pthread pool; OpenMP is disabled) and the native test executables, including the real-model suites and the stress loop's concurrent callers, second engines and router evictions, and the Rust binding's tests (one engine and one router shared across threads, cancellation set from another thread, close on a different thread). It does not cover the Node worker threads. No suppressions:

```sh
cmake --preset sanitize-thread -DDUCKTAPE_TEST_MODEL=/path/to/Laya-Q8_0.gguf
cmake --build --preset sanitize-thread && cmake --build build-sanitize-thread --target laya-stress
ctest --preset sanitize-thread
TSAN_OPTIONS=halt_on_error=1 LD_LIBRARY_PATH=build-sanitize-thread build-sanitize-thread/laya-stress /path/to/Laya-Q8_0.gguf 10
```

Rust needs the pinned nightly toolchain with `rust-src` (`rustup toolchain install nightly-2026-10-17 --profile minimal --component rust-src`, the `RUST_NIGHTLY` of `scripts/check-sanitizers.py`) and the instrumented library from the build above:

```sh
RUSTFLAGS='-Zsanitizer=thread -Clink-arg=-Wl,--export-dynamic' \
  DUCKTAPE_LAYA_LIB_DIR=build-sanitize-thread LD_LIBRARY_PATH=build-sanitize-thread LAYA_MODEL=/path/to/Laya-Q8_0.gguf \
  cargo +nightly-2026-10-17 test --locked -Zbuild-std --target x86_64-unknown-linux-gnu --lib \
  --manifest-path bindings/rust/Cargo.toml
```

`--export-dynamic` exports the runtime's interceptors to the shared library as a Clang link does; without it, guarded static initialization inside the library (`__cxa_guard_*`) is reported as a race. With a `vm.mmap_rnd_bits` above 28 (as on the CI runners), TSan needs `sudo sysctl -w vm.mmap_rnd_bits=28`. `scripts/check-sanitizers.py --only thread` runs all of this.

For coverage-guided request/planner/router fuzzing, use the `fuzz` preset (Linux, Clang). It instruments the shared core, every library source including its object libraries, and links libFuzzer only into the test executable. It needs no model; lazy inference is directed at a known non-model file. Generated/mutated corpus files and crash reproducers belong in ignored build directories. Preserve minimized regressions in tests after triage.

```sh

python3 tests/fuzz-corpus.py build-fuzz/corpus

UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1 \

```

This covers instrumented library parsing, planning and router boundaries; it does not claim coverage-guided testing of upstream tensor kernels or model loading. Do not package the instrumented library. Short smoke runs exercise the harness; they do not satisfy the one-hour qualification budget.

Use the campaign runner to retain identities, seeded corpus, commands, statistics and failures for qualification (the CI `qualify-fuzz` job runs it):


## Reproducible builds

Independent reproducibility compares the bytes, permission bits and symlink targets of all installed native and Node files from a single captured working-tree snapshot compiled in two separate source/build/install roots. Runtime source is archived from its recorded commit and patches are hash checked. The report identifies dirty source and hashes the actual snapshot. The guarantee is for the same toolchain and options; it does not assert identical output across compilers or architectures. Packaging determinism is a separate check for identical prebuilt inputs.

`scripts/check-reproducibility.py --output build-repro-new` compiles one captured source snapshot in two independent source/build/install roots and compares all installed native/Node bytes, modes and symlink targets. Source/build paths are normalized; generated GGML identity uses the explicit runtime pin. Keep Node build/install RPATHs relative to `$ORIGIN`, and package the installed addon. Installed consumer tests reject absolute library search paths.

On Windows, clang-cl builds with `/Brepro` (no timestamps in objects; a content hash instead of the link time in the DLL, addon and import library), and CI runs the same check from a Visual Studio x64 developer prompt:

```bat
python scripts/check-reproducibility.py --output build-repro --cc "%CLANG%" --cxx "%CLANG%" --node-include "%NODE_INCLUDE_DIR%" --cmake-arg=-GNinja "--cmake-arg=-DNODE_LIB=%NODE_LIB%" "--cmake-arg=-DDTL_PATCH_EXECUTABLE=C:/Program Files/Git/usr/bin/patch.exe"
```

This check covers identical inputs and toolchains, not different compilers or architectures. Across hosts, the Linux x86-64 library and Node addon built by CI (`ubuntu-24.04`, gcc 13.3.0, Node 26.7.0 headers) are byte-identical to the release host's build of the same commit; the release procedure compares their hashes (`library_sha256`, `addon_sha256`) and stops when they differ. Keep its reports in CI/PR artifacts or ignored build directories. A reproducible build is one release requirement, not a substitute for runtime, platform or installed-consumer checks.

Native packaging rejects binaries exposing sanitizer, libFuzzer coverage or LLVM profile instrumentation symbols (on Windows and macOS also binaries that load a sanitizer or debug runtime) before loading them. Use separate diagnostic builds for testing and rebuild uninstrumented release artifacts for distribution.

The DLL's bytes depend on the runner image, not only on the sources: it links the image's MSVC and Windows SDK libraries (UCRT, vcruntime), and two images built different, individually reproducible DLLs from one commit. Package inventories and reports therefore record `build_environment` (`ImageOS`, `ImageVersion`, `VCToolsVersion`, `WindowsSDKVersion`, `VSCMD_VER`), and the reproducibility check must run on the image of the build it validates; it rejects a reproduction from another environment. An ordinary Linux host sets none of these variables, and Linux x86-64 builds with the same compiler and Node headers matched across hosts (below).

`validate.py` writes the native fixture results to `outputs.json` (from `tests/parity.py --report`); `check-candidate.py` accepts browser drift only against that file of the candidate's native run. The comparator requires matching fixture sets, native key order mapped to JavaScript property order, a responsive main-thread heartbeat, ordered events and finite values. It reports numeric drift and changed choice/structured decisions without a cross-profile tolerance gate. Metadata, token counts and result shapes remain exact. `tests/compare-browser-reference.py` separately compares with unchanged upstream decision processing on the same backend.

For repeatable real-browser runs, install the locked developer tools (`qualify-host.py` does) and use an installed Chrome. Build both backend reference probes with `--reference` first, and the constrained WASM test build for the `memory` stage:

```sh
python3 scripts/build-browser.py --emsdk EMSDK --backend wasm --maximum-memory 469762048 --build build-browser-wasm-constrained
npm ci --ignore-scripts --prefix tests/browser-automation
node tests/browser-automation/run.mjs --model /path/to/Laya-Q8_0.gguf \
  --native build-check-native/outputs.json --constrained-wasm build-browser-wasm-constrained --output build-browser-check
```

The runner starts its own loopback-only harness, verifies the model, runs both backends, upstream comparisons, lifecycle/assets/device-loss checks, WebGPU allocation failure (`gpu_memory`: a test worker fails chosen GPU buffers; opening and a router's model-loading request must reject with status 2, a failed weights buffer while loading the model and a failed compute buffer while creating the inference context (checked by their messages), the router must keep answering unchanged, and the page must then open a working engine), and closes the browser and server afterward. It records browser/platform, model, fixture and asset identities. Same-backend upstream failures cause a failed exit; cross-profile drift is retained as measured evidence, not probability equivalence. It defaults to headed Chrome without custom launch flags; use `--headless` only when that environment provides the intended GPU. `--isolated` serves the page with COOP/COEP (cross-origin isolated) and runs that page's own stage list. `--package-dir EXTRACTED_PACKAGE` tests shipped assets; `--backend wasm|webgpu` selects a backend. Explicit `--skip-reference`/`--skip-controls` leave those checks not run. `--constrained-wasm BUILD` adds a WASM `memory` stage using a test build with a lowered heap ceiling (`scripts/build-browser.py --maximum-memory 469762048`, 448 MiB): opening an engine and a router's first request there must reject, never hang or succeed, and the page must then open a working engine with the product build. `check-candidate.py` requires it in both browser reports, like the WebGPU `gpu_memory` stage. Packaging rejects builds whose ceiling is not 4 GiB. Selected-check success is never full release approval.

The stages each page must pass, per backend (`check-candidate.py` requires each):

| Page (evidence key) | WASM | WebGPU |
|---|---|---|
| Not isolated (`browser`) | `execution`, `reference`, `controls`, `assets`, `upstream_numeric`, `memory`, `cross_profile_drift` | `execution`, `reference`, `controls`, `assets`, `upstream_numeric`, `device_loss`, `gpu_memory`, `cross_profile_drift` |
| Isolated (`browser_isolated`) | `controls`, `isolated_execution`, `running_cancellation` | `controls`, `isolated_execution` |

`execution` records the sha256 of every fixture result; `isolated_execution` runs `primitive.json` once on the isolated page, and the checker requires its result to be byte-identical to the non-isolated page's. `running_cancellation` (WASM only: the worker offers cancellation of a running request only when cross-origin isolated, through a `SharedArrayBuffer` flag) cancels a long request mid-pass, requires status 5, and requires the engine's next request to return the unchanged `primitive.json` result. The isolated page runs no other stage, since the rest do not depend on isolation.

Store run results in ignored build directories or CI/PR artifacts. Broader GPU, physical CPU and minimum-browser coverage are not covered yet ([roadmap](ROADMAP.md)).

## Security review

The `security_review` gate has no runner: the maintainer reviews the threat boundaries in `SECURITY.md`, the pinned dependencies' advisories and the release permissions, and writes `security_review` evidence by hand as a JSON object that `check-candidate.py` validates (`release_support.security_review_problems`):

| Field | Required value |
|---|---|
| `source_commit` | The candidate commit (or, for the hours-long reuse rule, an ancestor with no input change since) |
| `source_tracked_dirty` | `false` |
| `runtime_commit` | The runtime pin in `release/compatibility.json` |
| `runtime_patches` | The SHA-256 of each runtime patch in that record, in order |
| `release_blocking_code_issues` | A list; it must be empty to pass |
| `model_licence` | A non-empty string recording that the model and component licence obligations were reviewed (the `license_inventory` gate reads it) |

Other fields (notes, advisory references) are free-form and not checked: the gate proves the review was recorded against this candidate, not what it concluded.

The `model_upgrade` gate accepts `comparison.status` of `passed` or `failed` by design: a changed model is expected to change outputs, so it requires the candidate-model checks (`native_contracts`, `binding_conformance`, `abi`) to pass and the comparison to complete, not to match the baseline.

## The candidate check

`check-candidate.py` takes a JSON map of evidence names to report paths and writes `gates.json`:

```sh
python3 scripts/check-candidate.py build-candidate/evidence.json --candidate COMMIT --report build-candidate/gates.json
```

Run it from a checkout of the candidate commit (`git switch --detach COMMIT`), so the checker is the candidate's own; a dirty checker tree shows as `checker_tree_dirty`.

Tier-1 evidence names and what produces them (paths as used in a candidate directory `build-candidate/`; `MODEL`, `ML` and `TD` are the English, multilingual and typed-decisions files). `scripts/qualify-host.py` runs the host's commands and writes their keys into `build-candidate/evidence.json`; `scripts/fetch-ci-evidence.py` adds the CI ones:

| Evidence | Produced by |
| --- | --- |
| `native` | `CC=gcc CXX=g++ python3 scripts/validate.py --full --model MODEL --extra-model ML --extra-model TD --upstream-reference --test-jobs 1 --output build-candidate/native` (profile `host-full`, uncached) |
| `native_matrix` | A JSON list of `report.json` paths that together cover every compiler and Node version in `release/qualification.json`: the host's gcc report above (gcc 13.3.0, Node 26.7.0) and the CI candidate run's clang report (`native-x64-clang-node-<version>`, profile `ci-compiler`, the pinned LLVM 22.1.8) |
| `browser_package`, `browser`, `browser_isolated` | The browser package's `inventory.json` and the two `tests/browser-automation/run.mjs` reports ([browser](#browser)) |
| `userspaces`, `rollback`, `installed_release` | [Installed packages](#installed-packages), run on this host on the CI-assembled packages ([CI candidate run](#release-targets-and-the-ci-candidate-run)) |
| `electron` | The candidate run's `linux-x64` Electron run of the assembled npm package (`installed-linux-x64-real-model/electron.json`) |
| `cross_cpu` | `tests/cross-host.py compare` of the CI record and this host's ([above](#long-and-instrumented-gates)) |
| `sanitizers`, `fuzz`, `upgrade` | The CI qualify run (`qualify-sanitizers`, `qualify-fuzz`, `qualify-upgrade`; [above](#long-and-instrumented-gates)), or the same scripts run locally |
| `soak`, `stress` | One `scripts/check-stress.py --seconds 10800` run (at least 1,000 rounds), both keys naming its report ([stress and soak](#stress-and-soak)) |
| `reproducibility` | `scripts/check-reproducibility.py` on this host ([reproducible builds](#reproducible-builds)) |
| `performance`, `performance_<model id>` | `tests/benchmark.py` per model on an idle host, checked against its budget ([performance budgets](#performance-budgets)) |
| `model_upgrade` | `scripts/check-upgrade.py` with `--candidate-model TD` and `--candidate-manifest models/laya-typed-decisions.json` |
| `security_review` | The hand-written review ([security review](#security-review)) |

`scripts/fetch-ci-evidence.py` adds the candidate run's evidence (next section). Binding rules:

- A gate passes only when its evidence passed and is bound to the candidate commit, the validated library and packages, the browser package assets and the pinned model; missing evidence is `not_run`.
- In particular: the security review must name its `source_commit` and `source_tracked_dirty` (false) like other reports; the cross-CPU bundle must contain the candidate library; the rollback's previous side must be an earlier release whose source is an ancestor of the candidate; the native packages must be built from the candidate's source identity; browser runs must use a Chrome version listed in `release/qualification.json` and, for WebGPU, listed non-fallback hardware; and each reproduced build must contain the candidate library and Node addon (run `check-reproducibility.py` with the Node headers of the validated build).
- The checks that take packages (`installed_release`, `userspaces`, `electron`, `rollback`, the licence texts of every platform archive) use the release packages the candidate run assembled, which are what is published; `artifact_integrity` also requires the CI linux-x64 library and Node addon to be byte-identical to the locally validated ones, every release package to carry exactly each target's fragment payload, and the CI linux-x64 fragment to equal this host's own `package-native.py` run (`build-candidate/native/packages`) entry by entry (headers, CMake and pkg-config files, Python, Java and C# code, crates, SBOM; compared by entry name and sha256, not container bytes, because deflate differs between hosts; three host-toolchain stamps cannot be equal and are normalized or partly compared, each listed under `package_comparison` in `gates.json`: the `cmake_policy(VERSION 2.8.3...X)` line CMake writes into `ducktape_laya-targets.cmake`, the `.NET` runtime version in the NuGet `nuget.psmdcp` `lastModifiedBy`, and the javadoc jar, whose HTML depends on the exact JDK (CI pins Temurin 25.0.4), so only its manifest and the API page names are compared; measured on a real candidate run, every other entry, class files and DLLs included, was equal).
- The `electron` evidence must be the `linux-x64` run of the candidate `ducktape-laya-X.Y.Z.tgz`, and `installed_release` must be this host's own linux-x64 run (its `host` field: Linux x86-64, not GitHub Actions, a hostname other than the CI report's), not CI's `installed.json`.
- A candidate whose own release record or targets are invalid (empty `required_gates`, unknown gate, missing workflow) is rejected before any gate runs, and `ci-run.json` must name `adrian729/ducktape-laya`.
- Hours-long evidence (`soak`, `stress`, `fuzz`, `sanitizers`, `performance`, `upgrade`, `model_upgrade`) and the `security_review` may come from an ancestor commit when the diff since touches no library input (`src/`, `include/`, `cmake/`, `patches/`, `CMakeLists.txt`, the runtime record and pin, the model manifest) and none of that gate's own inputs: for the security review the binding code and package manifests (`bindings/**/package.json` included), `scripts/` and `.github/`; for fuzz its harness and `tests/fixtures/` (the corpus seeds); for sanitizers the native tests, their fixtures and `tests/original-reference/routing/`; for the others their harness files (`HARNESS` in `scripts/check-candidate.py`). Soak, stress and performance must also have run on the candidate's exact library bytes, and stress, soak and fuzz must meet the candidate's own budgets (`requested_seconds` against `routine_stress_seconds`, `candidate_soak_seconds` and `fuzz_seconds_per_target`, and the completed rounds against `candidate_soak_rounds`, of its `release/qualification.json`). A CI-produced `sanitizers`, `fuzz` or `upgrade` report counts only when `ci-run.json` lists it under `qualify_run` with its sha256; a report produced on a local host is checked as any other. Everything else (native validation, packages, browser runs, reproducibility, install checks, all tier-2 evidence) is produced from the candidate itself. The report lists reused evidence under `reused_evidence`.
- The release record, policy, budgets, notices and source identity are read from the candidate commit's own tree, read from the extracted candidate tree, and the checker runs from a checkout of that same commit, so what is checked is what is released.
- `release_ready` requires every gate of every release target. Publication is a separate step ([RELEASING.md](RELEASING.md)).

## Release targets and the CI candidate run

`release/compatibility.json` lists the release `targets` (schema 2). `linux-x64` is tier 1: every gate above, qualified on this host. `linux-arm64` and `windows-x64` are tier 2: CI-tested on `ubuntu-24.04-arm` and `windows-2025`, primary (English) model only, with the gates in `release/qualification.json` `target_gates`: `native_contracts`, `binding_conformance`, `upstream_reference`, `original_reference` (Windows may use only its documented `json_escaping/spam` deviation, capped at 0.06), `abi`, `installed_packages` (the assembled release packages, installed outside the checkout on the target's runner, Electron as directory and ASAR), `artifact_integrity`, `reproducibility`, `short_stress` (`budgets.short_stress_seconds`, 300 s, and at least `short_stress_rounds`, 40 rounds) and `cross_profile_drift` (drift against the tier-1 profile reported; any changed decision fails). Each target names its numerical profile, compiler and math library: Windows reports the same runtime profile label as Linux x86-64 (`native-cpu:avx+avx2+fma+f16c+bmi2+sse4.2`), but it is a clang-cl/UCRT build whose results differ slightly (see [COMPATIBILITY.md](COMPATIBILITY.md#known-deviations)); the record carries the distinction, the runtime label does not. Editing `release/compatibility.json` is a library input change: it invalidates reuse of hours-long evidence, so land record edits before a candidate's long gates start.

This host builds only Linux x86-64. The packages of every target, and the tier-2 evidence, come from one CI candidate run on the exact candidate commit: `gh workflow run native.yml --ref BRANCH -f mode=candidate` (the commit must be the branch head; `gh workflow run` cannot target a SHA). A candidate run runs everything on every platform and is never skipped as up to date:

| Job | Runs |
|---|---|
| `tooling` | `scripts/check-policy.py --all`; its success is part of the run's conclusion, which the checker requires |
| `build-<P>` (`linux-x64`, `linux-x64-clang`, `linux-arm64`, `windows-x64`) | `validate.py --full --phase build` with the model and the reference probe, through the compiler cache (none with `-f cache=off`); uploads the build directory as a tarball |
| Shards: `native-<P>` (Windows: `ctest-windows-x64` and `references-windows-x64`), `parity-a-<P>` and `parity-b-<P>` (arm64: one `parity-linux-arm64`), `packages-<P>`, `bindings-<P>` | `validate.py --phase test --from BUILD --checks ...`: the native tests with the examples, ABI and binary checks (`ctest`), the original and upstream references (`references`), the two halves of the full parity matrix (`parity:full-a`: C, C++, Rust, Node, Python; `parity:full-b`: C, Java, .NET, Go), the packages, and the binding suites with the four platform policy checks (`bindings`, `policy-platform`). On `linux-x64` the native shard also writes the cross-host bundle and record. The clang leg runs no packages or policy |
| `stress-linux-arm64`, `stress-windows-x64` | `check-stress.py --prebuilt --budget short` on the build's own library: 300 s and at least 40 rounds |
| `reproducibility-linux-arm64`, `reproducibility-windows-x64` | `check-reproducibility.py`, uncached, independent of the build job |
| `evidence-<P>` | `scripts/merge-validation.py --profile ci-full` (`ci-compiler` for clang) merges the shard reports into one report (`phase: merged`) and uploads `evidence-<platform>` (and `native-x64-<compiler>-node-<version>` on x64) with `stress-<platform>` and `reproducibility-<platform>` beside it |
| `assemble`, `assembled-<P>`, `musl` | The three fragments assembled into the release packages, installed with the real model on every target's runner (including Electron as directory and ASAR), and the musl check |

The merge refuses unless every shard passed, all of them share the build's source, fixtures, library, addon, CMake cache and registered tests, their checks together are exactly the profile's, the C results of the two parity halves are byte-identical, and the cross-host output comes from exactly the one shard that writes it; it copies each gate from the shard that owns its check, never recomputing it. The tier-2 `evidence-<P>` job also fails fast, before merging, with "image changed: rerun" when the stress or reproducibility job ran on a different runner image from the build (`build_environment`). The run keeps for 30 days: `evidence-<platform>` (validation report, `outputs.json`, reference reports), `packages-<platform>` (fragments), `packages-assembled` (the release packages), `installed-<platform>-real-model` (`installed.json`, `electron.json`), `stress-<platform>`, `reproducibility-<platform>` and the `native-x64-*` artifacts; the build tarballs and shard outputs are kept 7 days, so a failed shard can be rerun within the week (`gh run rerun RUN --failed`; only for environmental failures; reruns replace the job's artifacts). The reports record their toolchain environment (`build_environment`: the runner image and, on Windows, the MSVC toolset and Windows SDK). The reproduction must run in the validated build's environment: the Windows DLL links the image's MSVC and SDK libraries, and on 2026-10-22, during a `windows-2025` image rollout, a job on image 20261021.278.1 built a different (self-consistent) DLL from the validated one built on 20261007.264.1. The checker rejects a reproduction from another environment.

`python3 -I scripts/fetch-ci-evidence.py --candidate COMMIT --output build-candidate/ci --merge build-candidate/evidence.json` finds the newest successful complete candidate run of the commit (or takes `--run`; `--qualify` also takes the qualify run, [above](#long-and-instrumented-gates)), requires its head commit, `workflow_dispatch` event, success, workflow file and repository, downloads each artifact, checks the zip against GitHub's sha256 digest, extracts it without links, absolute or `..` paths (creating the parent of `--output`; an Actions zip keeps no file modes, so the executables a bundle lists in its `file-modes.json`, such as the cross-host bundle's `laya-conformance-c`, get their `755` back), and writes `ci-run.json` (the run and the sha256 of every file) and the evidence keys: `ci_run`, `release_packages`, and per target `<platform>:native`, `<platform>:fragment`, `<platform>:installed`, `<platform>:electron`, plus `<platform>:stress` and `<platform>:reproducibility` for tier 2. `check-candidate.py` stays offline: a CI file that is not listed in `ci-run.json` or has changed since fails its gate, as does a run of another commit or event. It warns when an artifact expires within 7 days; expired artifacts mean a new candidate run.

The CI linux-x64 library and Node addon must be byte-identical to this host's `validate.py` build of the same commit (gcc, Node 26.7.0 headers on both sides); check `library_sha256` and `addon_sha256` of `build-candidate/native/report.json` against `build-candidate/ci/evidence-linux-x64/report.json` as soon as both exist. Before concluding, redispatch the candidate run once with `-f cache=off`: if the uncached bytes match, the compiler cache was at fault (record it and use the uncached run); if they still differ, the difference is not environmental: stop and report (a toolchain or Node header change on one side). On this host, `scripts/qualify-host.py` runs the package checks on the shipped packages (the first three commands below, with `installed_release`, `userspaces` and `rollback` as their keys); the drift of each tier-2 target is measured by hand, with the last command per target:

```sh
python3 tests/installed-packages.py build-candidate/ci/packages-assembled MODEL --platform linux-x64 --report build-candidate/installed-release.json
python3 tests/linux-userspace.py build-candidate/ci/packages-assembled MODEL ROOTFS... --report build-candidate/userspaces.json
python3 tests/rollback.py LKG_PACKAGES build-candidate/ci/packages-assembled MODEL --report build-candidate/rollback.json
python3 tests/compare-profiles.py build-candidate/native/outputs.json build-candidate/ci/evidence-windows-x64/outputs.json --target-platform windows-x64 --report build-candidate/drift-windows-x64.json
```

and add `<platform>:drift` (one per tier-2 target, `linux-arm64:drift` and `windows-x64:drift`) to the evidence map. `gates.json` (schema 2) keeps the tier-1 gates under `gates` with their meaning unchanged, adds `targets` (`{platform: {tier, gates, ci_run}}`, the tier-1 target repeating the release-level statuses), records the release packages' inventory as `inventories_sha256.native`, and names the candidate run as `ci_run` (repository, workflow, run id and attempt, head commit), which `attest-release` checks the published native inventory against. `checker_tree_dirty` is true when the checker's checkout has tracked changes, or any untracked file under `scripts/` other than bytecode caches (the checker imports its modules from there); a dirty checker's report is never `release_ready`.

`scripts/validate.py` runs on every target; on Windows pass `--node-lib` and the clang-cl build through `--cmake-arg` (see the `generic-windows-x64` and `build-windows-x64` jobs in `native.yml`). Checks that do not apply are listed under `skipped` in `report.json` with the reason, never left out silently: fault injection (`real-faults`, `real-c-faults`, `real-runtime-faults`, `real-api-faults`, `ggml-faults`) is Linux-only (prctl, rlimits), the QEMU CPU guard is Linux x86-64 only (recorded as skipped on Windows and on Linux arm64), and the release checker and asset tests run on the Linux host only. Tests that CTest reports as skipped, and checks inside a passing test that print a `SKIPPED:` line (read from CTest's JUnit output, `ctest-junit.xml`), are recorded there too, as `<test>` and `<test> (partly)`. `SKIPPED:` is reserved for checks the host prevented; a check that does not exist on the platform (the Linux-only affinity probe, VmRSS and allocation-count checks) prints `NOT APPLICABLE:` and is not recorded. `check-candidate.py` refuses a report that records a registered test as skipped or any `(partly)` entry, so a candidate needs a host where every check runs. The non-ASCII hard-link check (`tests/native.cpp`) is skipped when the model cannot be hard-linked into the build directory, so the build directory must be on the model's filesystem. The report also records `platform`, `addon_sha256` and the registered native tests. On Windows the stress test measures committed private bytes (`PrivateUsage`) instead of `VmRSS`, the process handle count instead of descriptors, and threads from a Toolhelp snapshot excluding the workers Windows starts for its own thread pools (threads whose start address is in `ntdll.dll`: the loader's three workers, which retire 30 s after start-up, and I/O or timer workers, which can linger for minutes after their last work); every thread the process itself starts (`std::thread`, ggml's workers) is counted, and a thread pool the library leaked would still show as leaked handles. The baseline is taken once the counts have been stable for 40 s, and after each close the counts must return exactly to the baseline (within 60 s; `settle_waits` reports how often that wait was needed). The memory limits are the same.
