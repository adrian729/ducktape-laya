# Changelog

User-facing changes per release. Each section lists breaking changes first; "Release tooling" covers how releases are built and checked, which does not change the packages' behaviour.

## Unreleased

### Breaking changes

- **One API across the bindings.** The names, errors and configuration are the same in every binding ([API.md](docs/API.md#interfaces)); nothing below keeps a compatibility alias.
  - **Names.** The engine is `Engine` everywhere (`Laya` in Node, the browser and Java, `LayaEngine` in .NET are renamed; Node is `require('ducktape-laya').Engine`). Java and .NET `LayaConfig`, `LayaCallOptions` and `LayaStatus` are `Config`, `CallOptions` and `Status`, and Node's `ExecuteOptions` is merged into `CallOptions`. Python's `CancelToken` is `CancellationToken`. Java's `LayaClosedException` is `EngineClosedException`.
  - **Typed statuses and errors.** Every binding has a `Status` enum and its errors carry it: Python `LayaError.status`, Rust `Error.status` (the `status::X` constants are gone), Java `LayaException.status()` (the int constants are gone), .NET `LayaException.Status` (`Code` is removed), Go `Error.Status` of type `Status`, JavaScript `StatusCode`. Node and the browser gain real `LayaError`, `LayaLoadError` and `EngineClosedError` classes (they threw plain `Error`s). Java and .NET gain `LayaLoadException` (status 7), `LayaArgumentException` and an `EngineClosedException` that .NET derives from `ObjectDisposedException`; argument errors in Python and JavaScript carry status 1. A binding checks `package_version` and refuses a library of another release in Python, Java and .NET too (status 7).
  - **Go.** `Error.Status` is a `Status`; `ErrClosed` is a sentinel (`errors.New`) that every closed-engine error wraps in a fresh `*Error`, so `errors.Is(err, ErrClosed)` still matches and no error value is shared. `OpenRouter` takes a `*RouterConfig`; the JSON form is `OpenRouterJSON`. `Close` called from an `OnEvent` callback no longer deadlocks: it closes at once and the running call releases the handle, so `CloseDeferred` is removed. `Config` gains `MaxWindowsPerCall`, and invalid UTF-8 in `Overflow` or a temperature key is rejected with status 1 instead of being replaced with U+FFFD. A zero `Config` field still means unset, Go's one exception.
  - **Configuration shape.** Node: `Engine.open(path, { config: {native keys}, maxPending })`; the flat `threads`, `contextTokens`, `overflow` and `temperatures` options are removed. Browser: `open(model, options)` and `openRouter({models, max_loaded, auto}, options)` with the native settings in `options.config`; `modelUrl`, `sha256` (now part of the `model` or route), `models`, `contextTokens`, `overflow`, `temperatures`, `maxLoaded` and `auto` are no longer open options, and a route's settings are a `config` with native keys. Python takes `max_windows_per_call`; Rust `Engine::open(path)` has no config and `Engine::open_with(path, &Config)` replaces the two-argument form; `Config::temperature(k, v)` is `Config::temperatures(iter)`; `open_router` and `open_router_with` accept router JSON or a new `RouterConfig`. Java `openRouter` and .NET `OpenRouter` accept a `RouterConfig` (.NET with `Route` and `AutoRoutes`), and `Config.Threads` is `int?` in .NET.
  - **The core is the only validator.** Bindings no longer check threads, context tokens, temperatures or overflow names; the core rejects them with status 1. Bindings check only conversions (NUL, invalid Unicode, non-finite numbers). `null` options and `null` config mean the defaults, and in Python `threads=0` is now sent instead of meaning unset.
  - **Error order.** Closed engine, then argument conversions, then cancellation, then (Node and the browser) admission, then the native call; at open, conversions come before the library loads. An already-cancelled token, signal or context fails at once with status 5, with no native call and no events (Python, Java, Rust and .NET's synchronous `Execute` used to make the call). Node and the browser check a dead worker right after the closed check.
  - **Cancellation.** Rust's `CallOptions::cancel_flag(&AtomicU32)` is `CallOptions::cancellation_token(&CancellationToken)`, and the host-deadline feature (storing 6 in the flag) is gone from Rust: the token only cancels, and `timeout_ms` is the deadline (`dtl_cancel_flag` in the C API still supports 6). Java's `CancellationToken.reset()` is removed; use a new token.
  - **Paths.** Python accepts `bytes` and `os.PathLike`, and Python, Rust (non-UTF-8 paths on Unix) and Node (`Buffer`, `Uint8Array`, `file:` URL) pass POSIX path bytes unchanged. Java gains `Path` overloads of `open`; they use `Path.toString()`, so a non-UTF-8 POSIX path cannot pass in Java, and .NET takes `string` paths.
  - **Library overrides.** `DUCKTAPE_LAYA_LIBRARY` (the library file; Node: the addon file) and `DUCKTAPE_LAYA_LIB_DIR` (its directory) are the overrides in Node, Python, Java and .NET, and both must be absolute paths (a relative one is a load error). `DUCKTAPE_LAYA_ADDON`, Node's `addonPath` and `runtimeInfo` options, and Java's `-Dducktape.laya.library` are removed. Rust and Go choose the library at build time (`DUCKTAPE_LAYA_LIB_DIR` for the Rust build script, `CGO_LDFLAGS` for Go) and have no run-time override. A failed library load is no longer cached in Java; the next call retries.
- **A call that plans more than 256 forward passes now fails by default.** The new engine-wide config key `max_windows_per_call` (1..4096, default 256) raises or lowers the limit; pass 4096 for the earlier behaviour. A router takes the key only in its shared config, where it bounds the whole call; a route's own config that sets it is rejected. `dtl_info` reports `max_windows_per_call` for every engine and `limits.default_windows_per_call`. Applications that accept untrusted input should also set `timeout_ms` and filter `overflow` and `max_windows` ([SECURITY.md](SECURITY.md)).
- **Repeated JSON keys are rejected.** A request, open config or router config with the same key twice in one object fails with status 1; the last value used to win silently, so a policy layer reading the first value could see a different `model`, `state` or `overflow` than the library used. Nesting is limited to 64 levels, as documented (65 were accepted).
- **Model info `name` can be `null`.** `dtl_info` with an engine returns `"name": null` for a model without `general.name` metadata; it failed with status 2 although the model opened.
- **macOS loads absolute paths only and refuses a swapped library.** Python, .NET, Java and Node never `dlopen` a bare `libducktape_laya.1.dylib` on macOS (dyld would search `DYLD_LIBRARY_PATH`, run paths and the current directory); they load the bundled library, `DUCKTAPE_LAYA_LIB_DIR`, then `/opt/homebrew/lib` and `/usr/local/lib`. After loading, each asks `dladdr` which file provides the library and fails with status 7, naming `DYLD_LIBRARY_PATH`, when it is not the file it asked for. Java extracts the bundled library under a name that carries its SHA-256 prefix.
- **Accelerate is off on macOS.** `GGML_BLAS` and `GGML_ACCELERATE` are forced off, so macOS runs ggml's own CPU kernels; Accelerate's results depend on the macOS version and it starts libdispatch threads. Probabilities from a macOS source build can differ slightly from earlier builds.
- **Several `CMAKE_OSX_ARCHITECTURES` values are refused.** Configure one architecture per build and combine the libraries with `lipo` ([packaging](docs/PACKAGING.md#macos)).
- **Browser `backend: 'auto'`** no longer retries an invalid config or route (status 1) with WASM.

### Features

- **macOS packages for Apple silicon and Intel Macs (tier 2).** `macos-arm64` and `macos-x64` are release targets ([platforms](docs/PLATFORMS.md)): two `.tar.gz` archives, npm `native/darwin-arm64` and `native/darwin-x64`, wheels `macosx_14_0_arm64` and `macosx_14_0_x86_64`, NuGet `osx-arm64` and `osx-x64`, and the jar's `native/macos-arm64` and `native/macos-x64`. They need macOS 14 or newer and carry one architecture each; an application for both combines the libraries with `lipo`. Intel Macs need the same x86-64 CPU features as Linux, and Rosetta 2 is not supported. In a pre-check run the probabilities stayed within 0.0285 (arm64) and 0.0390 (x64) of the original Laya's, with no known deviation, and memory stayed flat in a 300 s stress run.
- **`noul` `labels`.** A `noul` question takes `"labels": {"false": "B", "true": "A"}` to rename the two option names the model reads, as the original Laya does; the answer is still the probability of true ([API](docs/API.md#primitive-requests-and-results)).
- **`scripts/evaluate-questions.py`** measures questions on your own labelled examples before you rely on them: AUC next to a text-length baseline and within length quartiles, precision and recall at a target precision with thresholds chosen on one half of the examples and measured on the other (alone and OR-ed with your current rule), and optional controls that reverse `choice` options or shuffle the state's words ([using Laya](docs/USAGE.md#measure-it-on-your-task)).
- **[Using Laya in an application](docs/USAGE.md):** where the models fit and where they do not, their known limitations with measured sizes (length and word-presence bias, missed requests that are not questions, uncalibrated probabilities, option order, `choice` favouring one option), which question phrasings helped and by how much, the cost per token, and a checklist for evaluating a task. The READMEs and API guide no longer call the probabilities calibrated without qualification.

### Fixes

- **Request parsing is linear.** Parsing request text took quadratic time in the number of objects (40,000 empty objects, 117 KiB, took 6 s, and no deadline or cancellation could stop it); it now takes milliseconds.
- **Error messages are valid UTF-8 of at most 1 KiB.** They could contain invalid bytes from paths or request text, and echo up to 1 MiB of a request.
- **`dtl_open` requires a regular file,** as routers already did: a FIFO path blocked the call.
- **No debugger on abort.** A ggml abort (an internal assertion, or a small allocation failing under memory pressure) ran `gdb` or `lldb` from `PATH` against the host process to print a backtrace; it now prints only the message before aborting.
- **`add_subdirectory` keeps the parent's `BUILD_SHARED_LIBS`,** which the build used to force off in the parent's cache.
- **Node.js and browser:** errors raised inside the Node addon (an open config over 1 MiB, an invalid argument) carry a status, and `NaN` or `Infinity` in a request object is rejected with status 1, where `JSON.stringify` would write `null`.
- **Python:** a request that cannot be serialized as JSON raises `LayaError` with status 1.

### Release tooling

- A `binding-abi` policy check keeps each binding's status codes and call-options layout equal to `include/ducktape_laya.h`.

## 0.3.0 (2026-10-26)

Packages for Linux arm64 and Windows x64 (tier 2) next to Linux x86-64 (tier 1) ([platforms](docs/PLATFORMS.md)). The C ABI stays 2 (`libducktape_laya.so.1`): code built against 0.2.0 keeps working, but the bindings report load failures and some errors differently, look up the native library more strictly, and prompts change for some structured values. `find_package(ducktape_laya 0.2 ...)` no longer finds the library (CMake package versions match the same minor version): request `0.3` or drop the version. Migration notes are in [docs/COMPATIBILITY.md](docs/COMPATIBILITY.md#migrating-from-020-to-030).

### Breaking changes

- **Node.js and browser errors.** Errors from the library and the worker now carry `status`, and every status-7 error carries the code `ERR_LAYA_UNSUPPORTED`: a missing, unloadable or wrong-ABI addon or WebAssembly runtime (0.2.0 threw a plain `Error`) and a CPU without the required features. `ERR_LAYA_CLOSED` and `ERR_LAYA_QUEUE_FULL` have status 1, `ERR_LAYA_WORKER_EXITED` status 3. In Node.js, `info()` after `close()` rejects with `ERR_LAYA_CLOSED` (it gave `ERR_LAYA_WORKER_EXITED` once the worker had exited), and a worker that crashes or cannot be reached rejects with `ERR_LAYA_WORKER_EXITED` (status 3) instead of passing the raw error on. A `null` or non-object options argument to `open`, `openRouter`, `execute`, `close` and Node's `Laya.runtimeInfo` is a status-1 `TypeError` (0.2.0 threw an untyped `TypeError`, except the browser's `openRouter(models, null)`, which worked), and so is a Node `addonPath` that is not a non-empty string (0.2.0 threw an untyped `TypeError` for a non-string, ignored an empty string, and gave a plain error for a missing file, which is now status 7 with `ERR_LAYA_UNSUPPORTED`). In the TypeScript types, `LayaError.status` is no longer optional and `code` adds `'ERR_LAYA_UNSUPPORTED'`.
- **Browser statuses.** A cancelled `open` rejects with status 5 (it was a `DOMException` named `AbortError`), a model asset that cannot be fetched or fails its `sha256` with status 2, an asset over `maxModelBytes` with status 1, and a failed WebAssembly memory reservation with status 4; other runtime load failures, and a missing WebGPU adapter, are status 7, and open options that cannot be sent to the worker are a status-1 `TypeError`. With `backend: 'auto'`, such a model asset failure is no longer retried with WASM, which would fail the same way. Running out of GPU memory is status 2 instead of ending the worker (see Fixes).
- **Python and .NET load failures are status 7**, as in Java and Node.js. Python raises `LayaLoadError`, a `LayaError` with status 7 that is still an `OSError` (it raised a plain `OSError`). .NET throws `LayaException` with status 7 and the loader's exception as `InnerException` (it threw `DllNotFoundException`).
- **Stricter library lookup.**
  - .NET tries the library bundled in the package (`runtimes/<rid>/native/`) before the system's, so an installed `libducktape_laya.so.1` (`LD_LIBRARY_PATH`, ldconfig, `/usr/local/lib`) no longer shadows it. A bundled library that fails to load or has another ABI is an error instead of a reason to try the system's. On Windows the system fallback searches only the assembly directory and the safe system directories, not the current directory or `PATH`; on Linux it uses the dynamic loader's search.
  - The Node addon on Linux finds its library through a `DT_RPATH` (`$ORIGIN`), which is searched before `LD_LIBRARY_PATH`, so the library shipped next to the addon is always the one used; the addon also refuses a library of another package version (status 7).
- **Big integers in structured values.** Integers outside the 64-bit range keep all their digits in the prompt, as the original Laya writes them (0.2.0 wrote `100000000000000000000000` as `1e+23`), so prompts and results change for such values. A `score` answer's `legend` also writes them with all their digits, as the request gave them (0.2.0 wrote them as floats).
- **Serialized state limit.** When the request runs the model, a structured state whose serialized text exceeds 2 MiB is rejected with status 1, as a rendered question over 2 MiB already was. A state can serialize several times longer than its request text (`1e15` is written `1000000000000000.0`); the limit keeps the 1 MiB request limit bounding tokenization.

### Features

- **Packages for Linux arm64 and Windows x64.** The archives `ducktape-laya-VERSION-linux-arm64.tar.gz` and `ducktape-laya-VERSION-windows-x64.zip` (headers, `bin/ducktape_laya.dll`, the import library `lib/ducktape_laya.lib`, CMake and pkg-config files), wheels tagged `manylinux_2_38_aarch64` and `win_amd64`, and one npm package, one jar and one NuGet package that carry every platform's library and load the running one (npm from `native/<platform>-<arch>/`, the jar from `native/<platform>/`, NuGet from `runtimes/<rid>/native/`). The Windows DLL needs the Microsoft Visual C++ Redistributable.
- **Windows x64.** The library builds with clang-cl. The Node addon delay-loads Node-API from the host executable, so it loads in Node and in Electron. The Go binding builds with MinGW-w64 gcc against the import library ([Windows setup](bindings/go/README.md#windows)), and the Rust crate links `ducktape_laya.lib`. The bundled DLL is loaded by every binding: Java extracts it to `%LOCALAPPDATA%\ducktape-laya\<content hash>-<owner hash>` (or under `-Dducktape.laya.tmpdir`), a directory with an owner-only ACL that does not inherit from the parent and is checked and cleaned before each load; the Python wheel's library also loads in x64 Python on Windows on Arm (emulated). Router paths are UTF-8, and the CPU check requires FMA and F16C as on Linux. Windows on Arm is not supported: a build for it fails to open with status 7 when its CPU check cannot read the required features, instead of skipping the check.
- **Clearer load errors.** A bundled library that exists but cannot be loaded is reported as found, with the operating system's reason and the likely cause (glibc older than 2.38, a missing Visual C++ Redistributable), in Python, Java, .NET and Node, instead of "not found". On musl (Alpine) the Node, Java and .NET loaders say that the bundled glibc library cannot load (status 7) instead of failing with an opaque loader error; Java and .NET then use only a musl build found on the loader path. .NET adds the constructor `LayaException(int status, string message, Exception? inner)`.
- **No limit on runs of spaces.** The 0.2.0 limit of 4,096 consecutive spaces, which guarded one slow tokenization case, is removed: tokenization is now linear (see Fixes).
- **Rust:** `Engine::open` accepts any `AsRef<Path>` (non-UTF-8 paths fail with status 1).
- **Building from source:** CMake presets `dev`, `product` (the packaged configuration), `sanitize`, `sanitize-thread` and `fuzz` ([building](docs/BUILDING.md#cmake-presets)). The `dev` preset is a fast edit loop: Ninja, ccache shared across worktrees, `-O1` and precompiled headers where results cannot change, so a one-file edit rebuilds in seconds, and `ctest --preset dev` runs the model-free tests in about 2 s ([development loop](docs/BUILDING.md#development-loop)). Every test belongs to a tier (`generic`, `specialized`, `release`) and a category, selectable with CTest labels. The native tests are built by default only when ducktape-laya is the top-level CMake project; as a subproject `DUCKTAPE_BUILD_TESTS` defaults to `OFF` (or to the parent's `BUILD_TESTING`). Reconfiguring an unchanged tree no longer recompiles the 16 translation units built from patched or generated runtime sources. `tests/benchmark.py` also runs on macOS.
- **Documentation:** a short README, new guides for [models](docs/MODELS.md), [performance](docs/PERFORMANCE.md) (with a second machine), [platforms](docs/PLATFORMS.md) and [building](docs/BUILDING.md), and package READMEs that stand on their own on the registries, with links that stay valid across releases.

### Performance

The latency and memory tables in [PERFORMANCE.md](docs/PERFORMANCE.md) were measured on 0.1.0- and 0.2.0-era builds and have not been re-measured on an idle machine. The figures below were measured in 2026-10 on an 8-core x86-64 development machine that was running other work, so treat them as estimates.

- **Faster forward passes.** The decision graph evaluated the decision head of all three question types and the library read one; it now evaluates only the asked type's head (runtime patch `laya-selected-decision-head.patch`), with bit-identical scores. Each pass took about 12% less time with the English and typed-decisions models and 21 to 25% less with the multilingual one. ggml also no longer creates and frees a context on every pass (`ggml-cpu-init-once.patch`; a small saving, not measured).
- **Less memory per engine.** llama.cpp reserved and zero-filled `n_vocab` logits per prompt token that the decision graph never reads: about 98 MiB per 512 prompt tokens with the English and typed-decisions models and about 500 MiB with the multilingual one. It is no longer allocated (`llama-embeddings-no-logits-buffer.patch`, a backport of upstream ed019cd8b); outputs are byte-identical. The multilingual request near the 512-token limit used 479 MiB less resident memory.
- **Text is tokenized once.** Each piece of a prompt was tokenized once to count its tokens and again to store them, both doing the full work (about 4.3 s per pass, so about 8.6 s in total, for 1 MiB of ordinary text). It is now tokenized once into a buffer sized from the text; tokens are identical.
- **Browser model download.** The worker reads a model into one buffer sized from `Content-Length` instead of collecting chunks and copying them into another buffer.
- **A structured state is prepared once per request.** Every question copied the state, serialized it and replaced the model's marker text in it, about 56 to 117 ms per question for a 0.9 MB state. It is now prepared once per request and model; prompts are identical.

### Fixes

- **Slow tokenization of ordinary text.** Splitting text at special tokens took time quadratic in the number of matches, and the English and typed-decisions vocabularies match every run of 2 to 24 spaces, the multilingual one every newline. One request could hold an engine for minutes (on that development machine, 64 KiB of double-spaced text took about 31 s, and 1 MiB of log lines took minutes with the multilingual model). The split is now linear (`tokenizer-linear-partition.patch`), with tokens identical to those recorded before the change; the same 64 KiB takes 0.2 s.
- **Deadlines and cancellation during tokenization.** Tokenization did not check the call's controls, so a call over a long text ran its tokenization to the end (seconds for 1 MiB) before a deadline or cancellation took effect. Tokenization now counts its work over the whole call (words, merges, special-token passes and matches, and each KiB the special-token search scans) and checks the controls once per 1,024 units (`tokenizer-stop-check.patch`), also for text that special tokens split into short pieces, such as double-spaced English or newline-separated lines with the multilingual model. A stopped call ends with status 5 or 6 and the engine stays usable. `real-control-tokenize` requires a deadline or cancellation at a tenth of a 1 MiB state's tokenization to end the call within half of its CPU time. A cancellation callback may call into the library during tokenization; the outer call keeps its check. The regular-expression pre-split of the text into words and each word's symbol setup are still not checked, nor are the merges of the SPM, WPM and UGM tokenizers, which no supported model uses.
- **Automatic thread count ignored CPU limits.** `threads` 0 used up to 4 threads whenever the machine had 4 online CPUs, even when the process could run on fewer (`taskset`, a container's CPU quota); ggml's workers wait by spinning, so 4 threads on 1 allowed CPU ran 1.6 to 2 times slower. The automatic count is now also at most the CPUs in the affinity mask (on Linux that of the thread opening the engine, which ggml's workers inherit; on Windows the process's) and, on Linux, the smallest cgroup v2 CPU quota of the process's group and its ancestors, rounded up. An explicit `threads` is used as given.
- **Out of memory and thread limits during a pass.** When ggml's CPU work buffer could not grow, the backend kept the freed buffer, so a later call or closing the engine could crash; when the operating system refused a worker thread (`RLIMIT_NPROC`, a container's pids limit), ggml aborted the process. Both now fail the call with status 4 and leave the engine usable (`ggml-cpu-work-buffer.patch`, `ggml-thread-creation-failure.patch`).
- **WebGPU out of memory ended the worker.** When the GPU could not create a buffer for the model's weights, inference buffers or backend state, the worker's WebAssembly runtime aborted: opening rejected with status 3 (`ERR_LAYA_WORKER_EXITED`), and a router that loaded a model for a request was closed. Opening and such router requests now reject with status 2, and the router stays usable (`ggml-webgpu-allocation-failure.patch`); the WebGPU error scopes it uses stay balanced when an allocation exits by an exception, so later device errors are still reported.
- **No C++ exceptions through llama.cpp's and ggml's C functions.** A failed allocation while opening an engine (loading the model, reading its GGUF metadata, logging, creating the CPU backend and buffers, listing the CPU's extra buffer types), in tokenization or in a forward pass (`llama_encode`, creating a buffer, splitting the graph) could throw a C++ exception through a llama.cpp or ggml C function, which is undefined behaviour in the Windows build (clang-cl `/EHsc`). These now fail with a status, 2 from `dtl_open` and 4 from a request (`c-api-no-throw.patch`, `tokenizer-stop-check.patch`, `llama-encode-no-throw.patch`), with nothing left allocated by a failed GGUF read; the backend registry's and CPU device's one-time records, built by `llama_backend_init`, abort instead, as ggml's other small allocations do. Results are unchanged.
- **Go:** an `Engine` dropped without `Close` was never released (the engine referenced itself through its `sync.Cond`, so the finalizer never ran), and its model stayed in memory for the life of the process.
- **Java on Linux and macOS:** the extracted copy is deleted right after loading, so a killed JVM no longer leaves a 7 MB copy in `/tmp`; `-Dducktape.laya.tmpdir` selects the directory (for a `noexec` `/tmp`).
- **Maven jar manifest:** the 0.2.0 jars (main, sources, javadoc) carry an unreadable `META-INF/MANIFEST.MF` (literal `\r\n` instead of line breaks), so `Implementation-Version` and `Automatic-Module-Name` were lost; the library still loads, since `module-info.class` is present.
- **C++:** `ducktape::info()`, `engine::open` and `engine::open_router` refuse a library of another ABI with `ducktape::error` status 7, and `engine::info()` on a moved-from engine throws instead of returning runtime info. Rust checks for a null info result.
- **Node addon built from source:** its run path had empty entries (`$ORIGIN::::`), which glibc resolves to the current directory; it is now `$ORIGIN:$ORIGIN/../..`.
- **CPU profile pinned at configure time:** ggml turns off AVX, AVX2, FMA, F16C, BMI2 and SSE4.2 when `SOURCE_DATE_EPOCH` is set or when cross-compiling, which would have built a different numerical profile without notice. The x86-64 options are now set explicitly; the Linux x86-64 build keeps the same profile and flags.
- **Hardened builds:** the library, ggml, llama.cpp and the Node addon are built with `-fstack-protector-strong`, `_FORTIFY_SOURCE=3` when optimising, full RELRO (`-z relro -z now`), `-mbranch-protection=standard` on Linux arm64 (return-address signing; not BTI, see the [roadmap](docs/ROADMAP.md)) and Control Flow Guard (`/guard:cf`) with clang-cl, instead of relying on the compiler's defaults. Linux libraries and addons ship stripped (dynamic symbols kept), and the npm package ships one copy of the Linux library instead of two.
- **Package metadata:** the wheel, npm, NuGet and Maven packages declare the licence `MIT AND Apache-2.0` (they bundle the Apache-2.0 Laya language data and an Abseil snippet), the browser package `MIT AND Apache-2.0 AND Apache-2.0 WITH LLVM-exception AND BSD-3-Clause`; the notices now attribute the code embedded in the vendored nlohmann/json header. Package descriptions no longer say Linux only, and `bindings/python/pyproject.toml` and `bindings/java/pom.xml` match the released packages. The NuGet assembly is built without a PDB, so every platform packs the same assembly.

### Platforms

- **Release targets and tiers.** `release/compatibility.json` (schema 2) lists the release `targets`: `linux-x64` tier 1 with every release gate, `linux-arm64` and `windows-x64` tier 2, tested in CI with the English model ([qualification](docs/QUALIFICATION.md#release-targets-and-tiers)). Probability drift from Linux x86-64 on the fixture corpus, measured in a CI candidate run: arm64 0.0334, Windows 0.0865, no changed decision. `tested_backend` is removed.
- **Windows known deviation.** One answer of the original-Laya comparison (`json_escaping/spam`, 0.0541 against a separate 0.06 cap) differs because the Windows C runtime's `erff`, `sinf` and `cosf` round differently from glibc ([compatibility](docs/COMPATIBILITY.md#known-deviations)).
- **macOS arm64** packages are built and tested in CI (minimum macOS 14) but not released.
- **musl (Alpine) stays unsupported.** CI runs the npm package and the jar in Alpine containers and checks that both report the glibc requirement.

### Release tooling

- **Multi-platform candidates.** `scripts/package-native.py` (formerly `package-linux.py`) packages the platform it runs on and `scripts/assemble-packages.py` merges the platforms' outputs. `native.yml` dispatched with `mode=candidate` builds, packages, assembles and installs every target on GitHub-hosted runners; `scripts/fetch-ci-evidence.py` downloads and hashes that run, and `scripts/check-candidate.py` checks every target (`gates.json` schema 2, with the run as `ci_run`). The CI Linux x86-64 library and Node addon must be byte-identical to the release host's validated build.
- **Bound releases.** `attest-release` and every `publish-release` job require `gates.json` to pass exactly the gates and targets of the tagged commit's release record, and the native inventory to be that of the candidate run `gates.json` names. The attestation signer is pinned by exact certificate identity. Retried publishing skips only registry versions whose contents equal the release files (`scripts/registry-state.py`, `scripts/pypi-missing-wheels.py`). `scripts/release-notes.py` renders the GitHub release text from this changelog.
- **Build evidence.** The build records the runtime sources each link of the library compiled, and packaging refuses a library linked from other sources ([build records](docs/BUILDING.md#build-records)). The release host's evidence, the reproducibility builds and the browser release builds are built without a compiler cache; CI builds use one, and every shipped library and Node addon is compared byte for byte with an uncached build. Binaries holding unmapped source paths are refused. `package-native.py` checks the shipped binaries' hardening, and `check-release.py` that the docs naming the current release name its version.
- **More checks.** Cancellation inside the forward pass (`real-control`), the WebGPU allocation failures (`gpu_memory`), tokenizer goldens and the decision-head comparison for every model, reconfiguration without recompiling, every example request (`tests/examples-smoke.py`, not on Windows) and the Markdown links and anchors (`tests/docs-links.py`). Tests open models through non-ASCII paths on every platform, and the binding suites test library lookup, extraction and musl detection.
- **CI.** Each job runs only when its inputs changed since its own last success (`scripts/ci_paths.py`, `scripts/ci-changes.py`): a branch push runs the policy checks it touched and one generic Linux job, a merge of an already verified tree runs nothing, and `main` runs the whole push profile. `scripts/verify.py` runs the stale specialized checks (bindings, packaging, sanitizers, fuzz, reproducibility, the real model, the browser, Windows, arm64, macOS) once per batch of changes, locally and in CI, and prints one verdict. Candidate runs build each platform once and run its checks in parallel shards, which `scripts/merge-validation.py` merges into one report. A nightly run keeps the compiler and model caches of `main` warm, and a weekly run checks everything with the real model. CI's clang is LLVM 22.1.8, pinned by archive hash. The .NET SDK, Node headers and JDK are pinned.
- **Release qualification.** `validate.py` runs the generic checks by default and the release evidence with `--full`, which refuses to report success when any check is missing; every report records which evidence profile it is. Sanitizers, the one-hour fuzz campaign and the runtime-upgrade rehearsal run in CI (`native.yml` `mode=qualify`, fetched with `fetch-ci-evidence.py --qualify`), and `scripts/qualify-host.py` runs the release host's gates in order, the soak pinned beside the others. The candidate soak is three hours and at least 1,000 rounds, serves as the routine stress, and fails on sustained memory growth (after the first quarter, at most 2 MiB median rise and 1 KiB per round); the tier-2 stress run is 300 s and at least 40 rounds. The cross-origin-isolated browser page runs its own stages, including cancellation of a running request.
- **Removed:** `validate.py --require-release`, `--skip-native-tests` and its `installed` suite (the installed checks run on the assembled release packages), `tests/parity.py --server-url`, and the mutation smoke `tests/input-fuzz.cpp` (the coverage-guided `laya-input-fuzzer` covers it). Evidence paths in `gates.json` are relative.

## 0.2.0 (2026-10-22)

C ABI 2 (`libducktape_laya.so.1`). Published on GitHub Releases, npm, crates.io, PyPI, NuGet, Maven Central and the Go module proxy, Linux x86-64 only. Breaking before 1.0, hence the minor version. Migration notes are in [docs/COMPATIBILITY.md](docs/COMPATIBILITY.md#migrating-from-010-abi-1-to-020-abi-2).

### Breaking changes

- **C ABI 2.** One `dtl_engine` handle for a single model or a router; `dtl_open(path, config_json)` and `dtl_open_router(router_json, config_json)` take a JSON config instead of `dtl_options`; `dtl_execute(engine, request, call_options)` is the only call, with the observer (`request_id`, `on_event`, `event_user_data`) inside `dtl_call_options`, whose cancellation user data is now `cancel_user_data`. `dtl_router*`, `dtl_decide*`, `dtl_execute_with_options`, `dtl_observer`, `dtl_options` and `dtl_default_options` are removed. New export: `dtl_cancel_flag`, a ready-made `should_cancel` that reads a host-set `uint32_t`. SONAME `libducktape_laya.so.1`, symbol version `DUCKTAPE_LAYA_2`.
- **Strict requests only.** The lenient legacy `decide`, which ignored unknown top-level fields, is removed from every binding. Unknown keys inside a question are rejected too (0.1.0 ignored them).
- **C++:** `ducktape::engine::open` and `open_router` replace `ducktape::laya` and `ducktape::router`; `execute` takes a `ducktape::call_options`.
- **Rust:** `Engine::open(path, &Config)` and `Engine::open_router(json, &Config)`; `execute` and `execute_with(json, CallOptions)` replace `decide*`, `execute_observed` and `execute_with_options`. `CallOptions` fields are private and set with builders (`request_id`, `timeout_ms`, `cancel_flag`, `on_event`); the cancel flag is a borrowed `AtomicU32` instead of an `AtomicBool` (nonzero cancels, 6 reports a host deadline), and `execute_with` takes the options by value. Status constants are in the new `ducktape_laya::status` module.
- **Rust `ducktape-laya-sys`:** `Router`, `Options`, `Observer`, `dtl_default_options` and the removed C functions are gone; `dtl_open_router` and `dtl_cancel_flag` are added, and `CallOptions` has the ABI 2 layout.
- **Node and browser:** `decide`, `decideStructured` and `decideBatch` are removed; `execute` takes one request or an array.
- **Confidence fields.** Every answer reports `answer_confidence` (the probability of the reported answer) and `confidence` (`1 − H(p)/log k`); the old `choice`/`score` `confidence` formulas are replaced.
- **Diagnostics.** Model info reports `context_tokens`, `trained_context_tokens`, `temperatures` and `metadata_temperatures` instead of `max_tokens`; the runtime limit `tokens_per_question` is now `default_context_tokens`.
- **Stored temperatures are bounded to [0.5, 5]**, as in the original Laya. With the English model this changes `choice` probabilities for 11 or more options (its stored `choice.11` is 0.1006).
- **Structured values are serialized as the original Laya does** (Python `json.dumps`: full float precision, `0`/`false` descriptions kept), so prompts for structured input change.
- **`"auto"` is reserved** and cannot be a router route ID.

### Features

- **Open config:** `threads`, `context_tokens` (prompt capacity, 32 up to the model's maximum (`trained_context_tokens`, 8,192 for the shipped files), default 512, replacing the fixed 512), `overflow` and `temperatures`, for an engine, for every route of a router, and per route. Requests may set `max_tokens`, `temperatures`, `overflow` and `max_windows`. Temperatures must be finite and positive after conversion to a 32-bit float (`1e-50` and `1e39` are rejected). Routes share a loaded model only when their path and configured values are equal, and each keeps its own default `overflow`.
- **Long input:** overflow policies `reject` (default), `truncate_end`, `truncate_start` and `scan`. Except under `reject`, over-long instructions and options are shortened as llama.cpp's decision server does; the question and options must still fit the limit on their own under every policy. Whenever the effective policy (the request's, or the engine's or route's default) is not `reject`, `usage` reports `state_tokens`, `state_tokens_dropped`, `truncated_questions` and `windows` (the most state windows any question used); scanned answers carry `window`. `"aggregate": "all"` makes a scanned `noul` question take the minimum over windows.
- **Choices:** `choice` criteria may be a list of labels; a single-option `choice` (and a one-value schema `enum`) is answered without inference.
- **Models:** the multilingual (F16) and typed-decisions (Q8_0) checkpoints, built with `scripts/convert-model.py` from `models/laya-multilingual.json` and `models/laya-typed-decisions.json` (no download URL yet). The text between mask tokens is tokenized on its own, as the models were trained; tokenizing the whole prompt at once dropped whitespace before a mask token with the multilingual vocabulary.
- **Routing by language:** a router's `"auto": {"english", "default"}` and requests with `"model": "auto"` and an optional `"lang"` (1–64 bytes); `usage.routing` reports the reason.
- **Runtime info:** features `language_routing` and `overflow_policies`, an `overflow_policies` list, and limits `minimum_context_tokens`, `scan_windows`, `object_members` and `windows_per_call`.
- **Bindings:** Python (PyPI), Go (module proxy), Java/Kotlin (Maven Central) and .NET (NuGet). Node `execute` and the browser take a `requestId`; the browser `openRouter` takes `auto` and per-model `contextTokens`, `overflow` and `temperatures`.
- **Node and browser errors:** both packages export `Status`; argument errors carry `status` 1; queue, closed and worker failures carry `code` `ERR_LAYA_QUEUE_FULL`, `ERR_LAYA_CLOSED` or `ERR_LAYA_WORKER_EXITED`.
- **Examples:** request presets in `examples/presets/` (support triage, email triage, prompt-injection screening, moderation).

### New limits (breaking)

These reject requests or configs that 0.1.0 accepted or that are new in 0.2.0. All fail with status 1.

- A JSON object in a request, an open config or a router config may have at most 1,024 members (`limits.object_members`).
- A run of more than 4,096 consecutive ASCII spaces in a question (instructions and options) or in the state is rejected: llama.cpp's tokenizer takes quadratic time on such runs, and tokenization cannot be interrupted.
- One call may plan at most 4,096 forward passes in total, counting every `scan` window (`limits.windows_per_call`).
- `score` levels must not be `null`.
- `context_tokens` below 32 is rejected when the config is parsed; the upper bound (the model's maximum (`trained_context_tokens`, 8,192 for the shipped files)) is checked when the model loads, which for a router route is its first request.
- `max_tokens` above the engine's `context_tokens` is rejected even when every question is a single-option `choice`.
- Integer settings (`threads`, `context_tokens`, `max_tokens`, `max_windows`, `max_loaded`) are range-checked correctly for integers above 2^63.

### Fixes

Changes to behavior that 0.1.0 already had:

- Model metadata strings longer than 255 bytes are read in full; 0.1.0 refused such models with status 2.
- `dtl_info` replaces invalid UTF-8 in model metadata instead of failing.
- Node and the browser reject strings that are not well-formed Unicode (lone surrogates) instead of replacing them.
- Node and the browser drop a call's `onEvent` handler once an abort or deadline has settled it.
- Node and browser `close()` resolve even when the worker has already exited or failed.
- The browser worker passes requests through heap memory instead of the 2 MiB WebAssembly stack.
- The Rust crate and the Node addon also call `dtl_abi_version()` and refuse any ABI but 2. In practice an ABI 1 library fails earlier, when the loader looks for `libducktape_laya.so.1` and its `DUCKTAPE_LAYA_2` symbols.

### Platforms

- **Windows x64 (in progress):** the library builds with clang-cl; the model-free native tests and the Python, Rust, Java and .NET suites pass in CI (the loaders find `ducktape_laya.dll`, Rust links its import library). Node, Go, packages and real-model checks are not ported yet. Text files are checked out with LF everywhere (`.gitattributes`), so patch and source hashes match on Windows.
- **macOS on Apple silicon** builds from a checkout and is tested in CI (macOS 15 arm64) with and without the real model; the library exports only `dtl_*`, uses an `@rpath` install name and checks dot product and FP16 at open. The Python, Java, .NET and Rust loaders find `libducktape_laya.dylib`. No macOS packages yet.
- **Linux arm64** builds (Armv8.2-A with dot product and half precision, checked at open like AVX2 on x86-64) and is tested in CI with and without the real model. Packaging on arm64 produces linux-arm64 packages (tarball, npm, wheel, jar, NuGet), and the Node, Python, Java and .NET loaders pick the library for their architecture; releases publish x86-64 packages only until arm64 is release-qualified.

### Performance

- A request's state is tokenized once and reused by its questions, instead of once per question.

### Release tooling

- New `original_reference` gate: the original Laya's recorded results, at the prompt length the original Laya runs each checkpoint at.
- `validate.py --extra-model` qualifies the additional models against the original and upstream references; `check-candidate.py` requires them.
- Release packages also include the Java jar (library bundled) with sources and javadoc jars and a POM, and the NuGet package (library bundled); both are byte-reproducible and tested installed, as is a Go consumer built against the tarball. The new models have their own performance budgets.
- `validate.py --packages` works without a model (`tests/package-smoke.py`), and CI runs it. `validate.py` records the Rust, Go, Java, .NET and Python versions, runs `tests/download-model.py`, and with a model requires the `cpu-guard` test.
- The rollback rehearsal handles an ABI break by building each side's consumer from its own source commit.
- `scripts/release-assets.py`: `assemble` builds the GitHub release asset set (renamed inventories and SBOMs, `gates.json`, `SHA256SUMS`) from the qualified package directories; `retain` turns downloaded release assets into the last-known-good package directory for `tests/rollback.py`.
- The `attest-release` workflow runs only from `main`, requires every gate passed, checks that the published inventories are the ones `gates.json` qualified and were packaged from the tagged commit, that every artifact they list is published with its hash, and attests nothing outside them.
- `check-candidate.py` binds more evidence to the candidate: the security review's source commit, the cross-CPU bundle's library, the rollback's previous side (an earlier release and an ancestor commit), the native packages' build source, the browser runs' Chrome version and non-fallback WebGPU hardware, and the reproduced builds' library.
- Browser builds record their optimization level and GPU tracing; packaging accepts only the product build from `scripts/build-browser.py` (`-O1`, no GPU tracing).
- Packaged tarballs normalize file modes (0644, or 0755 for directories and executables).
- `check-release.py` checks that the ABI version, SONAME, `exports.map` version node and header agree, and that scripts name the matching `.so`.
- The pkg-config file finds its prefix from multiarch library directories (`lib/x86_64-linux-gnu`).
